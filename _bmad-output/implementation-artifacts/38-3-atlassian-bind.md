## Story

As a **team on on-prem Jira and Confluence**,
I want `ma-atlassian-bind` to write each owned key into the upstream skills' override files between its own markers, refuse to touch a key we set ourselves, report a slot the installed skill does not declare, and take every line back out on `unbind`,
so that BMad's planning, build and product-owner skills publish to and read from our Confluence and use Jira as Sofia's store without anyone editing an upstream skill, and removing the module returns every skill to upstream behaviour byte for byte.

- **D1 Python, not `node`.** F29 `:129-132` and the Epic 38 scope list the "override generator" among four JavaScript scripts run with `node`. Upstream would install a `.js` (`setup.py:1672-1692` checks only `scripts/<file>`), so this is a choice, not a constraint. It is Python (PEP 723, standard library) because bind's job is TOML: it must parse each target file exactly as upstream does (`tomllib`, which `config_utils.load_toml` uses), and Node has no TOML parser — a hand-written one, or an npm package the offline runtime does not carry (the bundle's wheelhouse is Python-only, FR282), would be a second parser that can disagree with upstream's on the very files bind must refuse; its validation runs upstream's Python resolver; the repository rule is `uv run --no-cache` for every script (lint, FR304) and 37.2's `apply_block.py` is the marker-writer precedent; and `offline_activation.py` starts every `[skill] scripts` entry through uv. The three Confluence scripts (publish engine, page tree, collision check — the Confluence page-collision predicate of Epic 31, not bind's key collision) stay JavaScript in 38.4, as the 37.4 engine did. PO item (a).
- **D2 Created headers are marked on the header line.** `unbind` must remove a `[workflow]`/`[agent]`/`[tickets…]` header bind created, and only that one. A pair cannot bracket a header (the validator's `marker-pair-header`) and a separate comment line with the `ma-atlassian:` prefix is a `bad-marker` to the validator, so the header line itself carries `  # ma-atlassian:created` (the validator's header pattern allows a trailing comment). `unbind` removes such a header once its table holds nothing but blank lines, bottom-up, with the one blank separator line bind put before it.
- **D3 Byte-exact insertion and removal.** Lines are kept as (text, ending); inserted lines take the file's first line ending (else LF); inserting after a last line without a newline gives that line the ending and leaves the inserted last line without one, and removal does the inverse, so bind-then-unbind restores a file with no final newline. A key goes after the last key (or end marker) of its table's section, before trailing comments and the next header; a root key (`description` in the store file) before the first header. A pair whose answer changed is replaced in place with its own line endings.
- **D4 Collision scope.** One collision leaves the whole `<skill>.toml` unchanged (F29 "leaves the file unchanged"), the other keys of that file reported `not written`. A key in the personal layer `<skill>.user.toml` collides only when it would mask ours: a scalar (it replaces), not a list (it appends). In the store file a defined key is `kept`, not a collision (FR289 "only keys the file does not yet define").
- **D5 Missing slot includes a changed shape.** A slot is missing when the installed `customize.toml` lacks the key or declares it with another type than the table's `form` (a list where bind writes a string would fail the target's render). An earlier pair of ours for a missing slot is removed on bind, since `render_skill.py` halts on it.
- **D6 User-scoped answers are named, not copied, in the skill overrides.** `confluence_mcp_server` and `jira_mcp_server` are user-scoped (FR300); `_bmad/custom/<skill>.toml` is the team layer (setup's `.gitignore` there ignores only `*.user.toml`). So the texts embed the team answers (sites, spaces, root pages, project key) and tell the agent to read the MCP server name with `resolve_config.py --key modules.ma-atlassian.confluence_mcp_server` (the sweep checks that key). The store file follows FR289 literally and writes `[tickets] mcp_server` from `jira_mcp_server` — a user answer in a team file: PO item (b).
- **D7 The maps are referenced, not copied, in Sofia's facts.** FR289 says the identity clause and the maps reach `bmad-agent-po` as `persistent_facts`. The maps fact names `[tickets.types]` and `[tickets.status]` of the store config with the project and site, so a project that changes a map entry in its store file (F29 `:359`) does not leave a stale copy in a second file (FR293: no second record).
