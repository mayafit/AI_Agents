# Story 30.4: Deprecate the Demerzel (ML Scientist) Agent — Non-Destructively, New Installs Only

Status: review

## Story

As a **ma-agents maintainer preparing the BMAD v6.10.0 integration**,
I want the Demerzel (ML Scientist) agent — the `ma-agent-ml` skill, its 12 `ml-*` workflow
skills, and the `bmm-demerzel` agent registration — removed from what ma-agents ships to
**new** installs, while every **existing** install that already has this content keeps it
untouched, and users are told once, non-nagging, that the agent is deprecated,
So that v6.10.0's fail-loud `_copyResolvedSkills()` does not abort on a stale
`marketplace.json` listing, the shipped bundle stops carrying an agent nobody is
converting to Memory-agent format, and no existing user's project is silently mutated
on their next `update`.

**Runs in parallel** with Story 30.1 (the v6.10.0 confirmation gate) — this story does not
depend on the pin bump landing first.

**FR:** FR244, FR245, FR246, FR247 (supersedes FR193). **NFR:** NFR49 (non-destructive
preservation contract).

## Acceptance Criteria

1. **Given** `lib/bmad-extension/skills/`, **When** this story lands, **Then** the
   `ma-agent-ml` skill directory and the 12 `ml-*` workflow skill directories
   (`ml-ideation`, `ml-eda`, `ml-architecture`, `ml-detailed-design`, `ml-techspec`,
   `ml-infra`, `ml-experiment`, `ml-analysis`, `ml-hparam`, `ml-advise`,
   `ml-retrospective`, `ml-revision`) no longer exist on disk.

2. **Given** `lib/bmad-extension-plugin/skills/` (the generated bundle), **When**
   `npm run build:plugin` is re-run against the pruned source, **Then** the same 13
   directories are absent from the regenerated output — the generated tree is never
   hand-edited to achieve this; it is a pure function of the source tree.

3. **Given** `lib/bmad-extension/skills/module-help.csv` (source) and
   `lib/bmad-extension-plugin/skills/module-help.csv` (generated), **When** the removal
   lands, **Then** the 13 `bmm-demerzel`-keyed rows (12 `ml-*` + the `ma-agent-ml` agent
   row) are gone from the source CSV, and the generated CSV — rebuilt from source — agrees.

4. **Given** `lib/bmad-extension/.claude-plugin/marketplace.json.template` (hand-maintained;
   **not** regenerated by `build-plugin.js`), **When** the removal lands, **Then** the
   `ma-agent-ml` + 12 `ml-*` entries are removed from `plugins[0].skills[]`, so the
   rendered `marketplace.json`'s skill list matches the on-disk skill directories exactly
   (a missed edit here is the one failure mode that makes v6.10.0's fail-loud
   `_copyResolvedSkills()` abort the install — this is the load-bearing edit).

5. **Given** `lib/agents.js` and `lib/skill-authoring.js`, **When** the removal lands,
   **Then** the `bmm-demerzel` agent registration (the `{ id: 'bmm-demerzel', ... }` entry
   in `lib/agents.js`'s `CUSTOM_AGENTS`/registry array, and the `'bmm-demerzel'` entry in
   `lib/skill-authoring.js`'s `CUSTOM_AGENTS` list) is removed. (`bin/cli.js` carries no
   independent literal reference to `bmm-demerzel` or `ma-agent-ml` — it only imports from
   `lib/agents.js`/`lib/skill-authoring.js` — so no edit is needed there for the removal
   itself; `bin/cli.js` IS touched separately for the deprecation-notice wiring, AC 8.)

6. **Given** `MANIFEST.yaml`, **When** the removal lands, **Then** no `ma-agent-ml`/`ml-*`
   entry can appear in it going forward. (Verified as a structural fact, not a hand-edit:
   `generateSkillsManifest()` in `lib/installer.js` derives `MANIFEST.yaml` at install time
   from `listSkills()`, which reads ma-agents' own root `skills/` catalog — a catalog that
   never contained `ma-agent-ml`/`ml-*` in the first place, since those only ever shipped
   through the separate BMAD-extension-plugin pipeline covered by AC 1-4. No static
   `MANIFEST.yaml` template hand-edit exists to make.)

7. **Given** an **existing** install that already has `ma-agent-ml`/`ml-*` content
   deployed (in `.claude/skills/`, `.agents/skills/`, `.cline/skills/`, or any other
   agent's skill root), **When** that install runs `ma-agents update` under this
   version, **Then** the already-installed content is left completely alone — no
   auto-removal, no prompt-to-remove, no migration. (Contrast with the destructive
   `migrateRetiredSkills()` sweep in `lib/installer.js`, which purges genuinely retired/
   renamed skill IDs — `ma-agent-ml`/`ml-*` are deliberately **excluded** from
   `RETIRED_SKILL_IDS`/`RENAMED_SKILL_IDS`; deprecation is not retirement.)

8. **Given** any install or update run, **When** the run reaches the point where
   `migrateRetiredSkills()` is invoked (both call sites in `bin/cli.js`:
   `installWizard()` and `handleInstall()`), **Then** a one-time deprecation notice is
   printed to stdout informing the user that Demerzel (`ma-agent-ml` + `ml-*`) is
   deprecated and no longer shipped by default, and a `shown` flag is persisted to the
   project-root `.ma-agents.json` (mirroring the existing `profile`/`bmadModules`
   field-ownership pattern in `lib/profile.js`) so the notice **never prints again** on
   any subsequent run, on this or any other project using the same `.ma-agents.json`.
   No target agent/replacement is named (FR246 — no in-tool migration).

9. **Given** the six tests enumerated in `sprint-status.yaml` for this story
   (`extension-module-restructure.test.js`, `plugin-manifests.test.js`,
   `routing-parity.test.js`, `agent-injection-strategy.test.js`,
   `convert-agents-to-skills.test.js`, `uv-transition-resilience.test.js`), **When** the
   removal lands, **Then** each is reconciled to the new post-removal shape (see Dev
   Notes for the precise per-file deltas) and passes when run directly.

10. **Given** the routing-parity test's `PERSONA_SKILL_IDS` list is cross-checked against
    `.github/scripts/multi-tool-smoke-verify.sh`'s `PERSONAS` variable (test 4.1), **When**
    `ma-agent-ml` is dropped from the test's list, **Then** the shell script's `PERSONAS`
    string is updated in lockstep so the drift check itself does not fail.

11. **Given** a new cross-mirror drift test, **When** it runs after `npm run build:plugin`,
    **Then** it asserts that neither the source tree (`lib/bmad-extension/skills/`) nor
    the generated tree (`lib/bmad-extension-plugin/skills/`) contains `ma-agent-ml` or any
    `ml-*` directory, and that the two trees' skill-directory-name sets are otherwise
    identical (no other drift introduced as a side effect of this story).

12. **Given** a new test for the one-time notice, **When** it drives
    `showDemerzelDeprecationNoticeOnce(projectRoot)` (or equivalent) against a scratch
    `.ma-agents.json`, **Then** it asserts: first call prints the notice and persists the
    flag; second call is a silent no-op; the flag survives alongside pre-existing fields
    (`profile`, `bmadModules`) without disturbing them; a missing `.ma-agents.json` is
    bootstrapped correctly (mirrors `setProfile`'s bootstrap-on-absence behavior).

13. **Given** the deferred Demerzel → Memory-agent conversion follow-up referenced in
    `architecture.md`, **When** this story lands, **Then** FR193 is understood as
    superseded by FR247 (already annotated in the PRD/architecture; no further edit
    required by this story beyond what FR247 states).

## Dev Notes

- **Two independent skill-delivery pipelines exist** in this codebase and it is easy to
  conflate them: (a) ma-agents' own root `skills/` catalog, installed per-agent via
  `lib/installer.js`'s `listSkills()`/`performInstall()`/`generateSkillsManifest()` — this
  catalog **never contained** `ma-agent-ml`/`ml-*`; and (b) the BMAD-extension plugin at
  `lib/bmad-extension/skills/` (source) → `lib/bmad-extension-plugin/skills/` (generated,
  via `scripts/build-plugin.js`), staged into a BMAD install via
  `.claude-plugin/marketplace.json.template` — this is where Demerzel/ML actually lives.
  AC 6 exists specifically to head off the natural mistake of hand-editing a
  `MANIFEST.yaml` template for pipeline (a) when the real fix is entirely in pipeline (b).
- **`bin/cli.js` has no independent `bmm-demerzel`/`ma-agent-ml` literal.** A grep across
  the file confirms it only imports `CUSTOM_AGENTS`/agent registrations from
  `lib/skill-authoring.js`/`lib/agents.js`. `sprint-status.yaml`'s phrasing ("remove...in
  bin/cli.js") is read here as "no residual reference survives in cli.js once the two
  library files are fixed" — verified true, not requiring a direct edit — plus the
  separate, additive notice-wiring change (AC 8) that DOES touch `bin/cli.js`.
- **`.agents/skills/` in this repo's own working tree still contains `ma-agent-ml`/
  `ml-*`.** This is this repo's own self-hosted (dogfooded) install of ma-agents onto
  itself, tracked in git. It is treated as an **existing install** under NFR49/AC 7 and is
  deliberately **not** touched by this story — touching it would contradict the very
  non-destructive guarantee this story exists to prove out.
- **Existing precedent for the notice mechanism**: `lib/profile.js` already owns
  read/write of the project-root `.ma-agents.json` for `profile` (`getProfile`/
  `setProfile`, with bootstrap-on-absence via `bootstrapRootManifest()`) and
  `bmadModules` (`getBmadModules`/`setBmadModules`). The new `notices` field follows the
  identical shape and bootstrap behavior rather than inventing a new manifest-access
  pattern.
- **`RETIRED_SKILL_IDS`/`RENAMED_SKILL_IDS` in `lib/installer.js` is the wrong tool for
  this job** — it is a destructive sweep (deletes manifest entries + deployed
  directories on every install/update). Deliberately not touching it is itself part of
  the AC 7 contract; a regression that adds `ma-agent-ml`/`ml-*` to either list would
  silently violate NFR49.
- **CSV row / directory count arithmetic**: 63 total skill dirs in
  `lib/bmad-extension/skills/` today (confirmed by reading
  `extension-module-restructure.test.js`'s existing assertions) − 13 (`ma-agent-ml` + 12
  `ml-*`) = 50. Same delta applies to `module-help.csv` row counts (63 → 50) in both the
  source and (post-rebuild) generated CSV.
- **Docs are explicitly out of scope.** `README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`
  reference Demerzel/ML historically; no test asserts on their content, and
  `sprint-status.yaml` assigns doc updates to Story 30.8. Left untouched here.
- **FR193 supersession (AC 13)** is already reflected in `architecture.md` (P5-8 edit,
  2026-07-09) and `prd.md` FR247; this story does not re-edit planning docs.
