# Story 32.8 — `AGENTS.md` Two-Writer Integration Test

Status: backlog
Blocked on: 32-3
Wave: 3 (parallel with 32.7)

**FR:** FR278 (second half: "the `AGENTS.md` two-writer case … is covered by an integration test asserting neither writer clobbers the other's block or user prose"). **NFR:** NFR46 (byte-identical in-marker content on re-stamp), NFR49 (user content preserved). **Decision inputs:** P5-10.5; impact analysis §4 M1.

## Story

As a **user who hand-edits `AGENTS.md` in a project that has both ma-agents (with OpenCode selected) and upstream `bmad-project-context`**,
I want each tool to touch only its own delimited block,
so that running either one — in any order, any number of times — never deletes the other's block or my own prose, and uninstalling ma-agents leaves upstream's block and my text intact.

## Context

ma-agents writes `AGENTS.md` only for the OpenCode target: `lib/agents.js:313` registers `{ template: 'agents-md.template.md', target: 'AGENTS.md', merger: 'markdown-markers' }`, processed by `markdownMarkersMerger` (`lib/installer.js:1332`), which uses `<!-- MA-AGENTS-START -->` / `<!-- MA-AGENTS-END -->`. When `AGENTS.md` does not exist it writes the **whole template** with a leading "Generated by ma-agents" comment (`lib/installer.js:1342-1345`), otherwise it replaces only the marker block. On uninstall, `lib/uninstall.js:45-51` lists `AGENTS.md` among the five injection files; `stripMarkerBlock` (regex at `:61`) removes the marker block and the file is **deleted** if what remains is blank (`:222-224`). Upstream v6.11 made `bmad-project-context` write "one verified block" into the repository's `AGENTS.md`, and v6.12 changed it to adopt a handwritten `AGENTS.md` rather than auto-rewriting it ([NOTE]-level in the impact analysis; 32.1 AC9(e) records the actual marker strings and adoption rule from the 6.12.4 source). Both writers appear to use delimited blocks, so coexistence is plausible — this story turns "plausible" into a test, because we tell users `AGENTS.md` is safe to hand-edit. The existing `test/agents-md.test.js` (22 tests) covers ma-agents alone.

## Acceptance Criteria

All ACs run against real writers: ma-agents' through its exported install path (OpenCode selected), upstream's through the 6.12.4 `bmad-project-context` mechanism as installed by 32.3 — **not** a hand-written imitation of upstream's block. If upstream's block insertion is LLM-driven instructions rather than a script, the test drives the deterministic part 32.1 AC9(e) identified (template + markers) and the Verification record says exactly which part was simulated and why.

1. **Order A (ma-agents first).** Empty project → ma-agents install (OpenCode) → upstream `bmad-project-context` block write. Assert: the MA-AGENTS block is byte-identical to its pre-upstream content; upstream's block is present exactly once; ma-agents' leading comment and template prose either survive verbatim or the record states upstream's documented adoption rule replaced them (and that is then flagged to the PO as a UX finding, not silently accepted).
2. **Order B (upstream first).** Empty project → upstream block write → ma-agents install. Assert: upstream's block is byte-identical before/after; the MA-AGENTS block is present exactly once; ma-agents did **not** write its full template over an existing file (only the marker block was added).
3. **User prose, both orders.** A fixture `AGENTS.md` with user paragraphs **before, between and after** the two blocks: after each writer re-runs (twice each, interleaved), every user paragraph is byte-identical and in its original relative position.
4. **Idempotence.** Re-running either writer with unchanged input leaves the file byte-identical (NFR46), checked by sha256 before/after.
5. **Uninstall keeps upstream.** `ma-agents uninstall` on the Order-A and Order-B results removes only the MA-AGENTS block; upstream's block and all user prose remain; the file is **not** deleted (it is not blank). A third fixture with only the MA-AGENTS block and no other content is deleted — the existing blank-file rule still works.
6. **Marker non-interference.** Upstream's marker strings (from 32.1 AC9(e)) do not match ma-agents' `stripMarkerBlock` regex (`lib/uninstall.js:61`) and ma-agents' markers do not match upstream's block detector. Asserted by feeding each tool's block to the other's matcher.
7. **CRLF.** Repeat AC1–AC3 with the fixture saved with CRLF line endings; no writer converts the other's block or the user's prose to LF (byte compare). (Mixed CRLF/LF in composed blocks is a known class in this repo — Epic 27.10.)
8. **Removal list reviewed.** `lib/uninstall.js` `INJECTION_FILES` is reviewed against 6.12.4: if upstream now writes any of `CLAUDE.md`, `.clinerules`, `.cline/clinerules.md`, `.roo/rules/00-ma-agents.md`, the same two-writer assertions (AC3, AC5) are added for that file. The review outcome is recorded either way.
9. **Mutation-checked.** (m1) `markdownMarkersMerger` writes the full template whenever markers are absent (even if the file exists) → AC2 red; (m2) `stripMarkerBlock` regex made greedy → AC5 red when a second marker-like block exists; (m3) the merger normalises line endings of the whole file → AC7 red; (m4) uninstall deletes `AGENTS.md` unconditionally → AC5 red.

## Dev Notes

- Use `os.tmpdir()` fixtures; never run against the repo root — the repo's own tracked `AGENTS.md` is already mutated by `npm test` (known), and this test must not add to that.
- Drive ma-agents via the same exported entry `test/agents-md.test.js` uses, with `MA_AGENTS_YES=1` (the merger's `yesMode`, `lib/installer.js:1335`).
- 32.1 records whether upstream's adoption rule treats ma-agents' generated template as "handwritten". If it refuses to write into a file that already exists (Order A), AC1's upstream-block assertion becomes "upstream reported it adopted the file" — record the exact behaviour and flag it.
- Only OpenCode triggers ma-agents' `AGENTS.md` write today; if the test needs a different tool to reach the merger, it is a sign the registry changed — stop and check `lib/agents.js`.
