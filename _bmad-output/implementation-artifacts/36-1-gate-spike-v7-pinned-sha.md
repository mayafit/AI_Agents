## Story

As the **ma-agents maintainer**,
I want every mechanism Epics 37–39 build on confirmed by running it against BMAD-METHOD at `e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6` in a scratch project,

## Context

This is a confirmation spike. The target is fixed (FR280: BMAD v7 at the commit in `bmadRef.core`); the spike does not reopen it. Its job is to turn each premise below into **[RUN]** or **[READ]** evidence.

Premises under test: the Skills CLI installs our modules from a local folder and from a tag, unattended and offline (AC2–AC4); `bmad setup` can be driven headless (AC5); upstream's validator accepts our module records (AC6); a `file:` or `https://` update source gives a usable `bmad status` (AC7); Sofia honours a project-defined store (AC8); the v6 migration handles a real 3.x project (AC9); the bind target slots exist (AC10); skills render offline from a wheelhouse (AC11); tea and cis publish v7 module records (AC12); the Skills CLI coexists with a 3.x install (AC13).

Premises that rest on upstream internals rather than documented behaviour, and are therefore the most likely to fail: (1) `setup.py --module-answers` is an internal contract (`skills/bmad/references/setup.md:47`); (2) `install_command()` returns a command only for `github:` sources (`skills/bmad/scripts/setup.py:1060-1066`), so a `file:` or `https://` module gets no install offer from `bmad status`; (3) a member skill's `source` must equal its record's `update_source` (`docs/reference/module-files.md:65`), so the update channel is baked into the published files, not chosen at install; (4) every skill activates through `uv run --no-cache … render_skill.py` (`skills/bmad-build/SKILL.md:12`), and `render_skill.py` declares `jinja2>=3.1` (`skills/bmad/scripts/render_skill.py:4`), so a warm uv cache does not help offline. All upstream citations in this story are at `e734d3a`.
