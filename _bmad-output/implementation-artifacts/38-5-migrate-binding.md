## Story

As a **team upgrading an ma-agents 3.x project that publishes to Confluence and tracks in Jira**,
I want `bmad migrate` to carry our 3.x binding into the `ma-atlassian` answers, take the 3.x publish blocks out of our override files without touching our own lines, and bind the upstream skills,
so that after the upgrade the planning, build and product-owner skills reach the same Jira project and Confluence space as before, and a second run changes nothing.

The script detects and deletes both families (a commented `MA-AGENTS-START` / `MA-AGENTS-END` pair, bare or as `<!-- … -->`), each pair closed by its own family. PO item (a).
- **D2 `project-layout.yaml` is kept.** The spec says the script reads it and is silent on its fate; deleting a file is the user's choice under `migrate.md`, and the 4.x upgrade backup already holds it. So that `detect` does not offer the migration forever, it also requires that no `ma-atlassian-migration-1.md` says `status: done`. PO item (b).
- **D3 Two stores: the other one becomes the tickets destination.** F29 asks which store becomes the planning destination; leaving the other unmapped would lose its space and root page, and 3.x's software store held epics and stories, which 4.x publishes to the tickets destination. The choice is `--planning-store system|software`; asked only while a destination answer is still pending. PO item (c).
- **D4 Answers only for pending questions.** `setup.py --module-answers` rejects an answer for a question that is not pending, and the 4.x installer asks the module's questions at install time, so on most upgraded projects the answers already exist. The script answers what is pending, keeps the rest, and reports a 3.x value that differs ("already answered; kept (the 3.x binding has …)"); it never edits the config files itself (FR288). PO item (d): whether the installer should leave `ma-atlassian`'s questions pending on a 3.x project so the migration supplies them.
- **D5 What 3.x never recorded.** `confluence_site` is required and never in a 3.x binding, so every Confluence project is asked for it once; `jira_mcp_server` and `confluence_mcp_server` take their default (empty: REST with ambient credentials). A root page maps to its id when 3.x recorded one, else its title (38.4's record-root-page records ids).
- **D6 Exit codes and arguments beyond the spec.** 0 done or nothing to migrate; 1 work left (a refused file, setup or bind failure); 2 prerequisite; 3 an answer or a choice is needed, nothing written. `--answer KEY=VALUE`, `--planning-store`, `--skills-root`, `--output-folder`, `--dry-run`, `--json`. `--skills-root` is needed because the spec's command runs the installed copy `_bmad/ma-atlassian/scripts/migrate_binding.js`, outside the skill folder, and setup and bind live in the skills folder; without it the script finds the one `<project>/<folder>/skills/ma-atlassian-bind`.
- **D7 Byte-exact deletion.** Files are read and written as latin1, so every byte round-trips; lines keep their own endings; a block's lines are dropped through the end marker's line ending, which is exactly what the 3.x writer added (`block + '\n' + rest`). A file left empty is kept (bind writes into it; `migrate.md` forbids deleting files). Multi-line strings are tracked so a marker quoted in one is not a marker.
- **D8 Backup and report.** Backups go to `.mv6/<run>/` (37.3's short folder, hashed names, `index.txt`, `.gitignore` `*`). The report is written when the run changed something or no report exists, and otherwise left unchanged; like 37.3's, a later run that changes something rewrites it. PO item (e): FR294 "never overwrites an existing file" read as applying to migrated data, not to the migration's own report.
