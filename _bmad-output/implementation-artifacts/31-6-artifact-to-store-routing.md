# Story 31.6 — Artifact-to-Store Routing Table

Status: review

**FR:** FR255, FR256, FR267; extends FR119, confirms FR120. **NFR:** NFR37, NFR82.
**Decision inputs:** P5-9.5 (store model), FR264 as amended 2026-08-02, OQ-5 as decided 2026-08-12.

This file is Story 31.6 AC6's deliverable: **the single reference every workflow is edited
against**, so a reviewer can check coverage without reading every workflow. It is not
documentation of the code — it is the specification the code is checked against.
`test/project-layout-artifact-routing.test.js` **parses the table below out of this file** and
measures each row against a **real `_bmad/bmm/config.yaml` generated by `generateBmmConfig`** from
real `project-layout.yaml` fixtures.

Because this document IS the deliverable, its shape is pinned as well as its claims (fix round —
the first round pinned only the claims, and a reviewer's mutation run then changed four rows'
destinations, deleted a row, added a row and deleted four whole sections with the suite fully
green):

- Each row's destination is checked against **the artifact it names**, resolved through the PRD's
  own requirement lines — never against the row's own group. Changing row 5 from software to system
  fails, because FR256 still says the architecture document is a software-requirements artifact.
- The **section set and the row set are fingerprinted**. Deleting a row (even with renumbering),
  adding one, or deleting a section fails and prints what changed. Editing this document is a
  deliberate act that updates the fingerprint in the same commit.
- Every **rule-source** cell must cite a requirement the PRD actually states, so `FR999` — or a
  citation quietly changed to something that does not exist — fails.

## 1. The three destinations

There are exactly three, and no artifact belongs to more than one.

| Destination | Binding record (`project-layout.yaml`) | Store path field (`config.yaml`) |
| --- | --- | --- |
| system requirements | `system_requirements_store` | `system_requirements_path` |
| software requirements | `software_requirements_store` | `software_requirements_path` (legacy alias: `knowledgebase_path`) |
| sprint management | `sprint_management` | `sprint_management_path` |

`sprint management` is **not a store**. FR267 is explicit that story files and everything else
under `implementation_artifacts` belong to *neither* knowledge store — they are sprint execution
state, and a project that moves its knowledge stores does not move its stories. It appears in this
table because a routing table with only the two stores would leave the reader to infer where the
rest goes, and inference is what this table exists to remove.

## 2. Directory derivation — how a store path becomes an artifacts directory

A store path field holds a **store location**, not an artifacts directory. `generateBmmConfig`
(`bin/cli.js`) already derives the directory for two of the three; the third follows the same rule.

All three rows are stated in ONE shape — *`field` when it is not `.`; otherwise `literal`* — because
the rule genuinely is one rule applied three times, and
`test/project-layout-artifact-routing.test.js` **parses these cells and evaluates them against the
real generator** rather than reading them as prose. The "config field" column names where the
generator writes its own answer, for the two destinations where it writes one.

| Destination | Artifacts directory | Config field the generator writes it into |
| --- | --- | --- |
| system requirements | `system_requirements_path` when it is not `.`; otherwise `{project-root}/_bmad-output/planning-artifacts` | none — workflows apply the rule themselves |
| software requirements | `software_requirements_path` when it is not `.`; otherwise `{project-root}/_bmad-output/planning-artifacts` | `planning_artifacts` |
| sprint management | `sprint_management_path` when it is not `.`; otherwise `{project-root}/_bmad-output/implementation-artifacts` | `implementation_artifacts` |

**Correction (fix round).** The system row previously read *"otherwise `planning_artifacts`"*. That
is right whenever both stores sit at `.`, and **wrong** in the one case that distinguishes them: a
project that leaves its system store here and moves only its software store. There
`planning_artifacts` IS the software store's directory, so the old wording routed the PRD into the
software store — contradicting Section 1's "no artifact belongs to more than one" and Section 3's
rows 1-4. The `.` branch is the *canonical local planning folder*, which is what
`planning_artifacts` also happens to equal when nothing has moved. The rule is now stated as the
value, and both branches are measured against `generateBmmConfig` — including that mixed case.

**Why the `.` case matters (NFR82).** In a single-store or legacy project all three store paths are
`.`, so the system and software directories collapse onto the one `planning-artifacts` folder and
every artifact lands exactly where it lands today. The two-store split is therefore *invisible*
until a store is actually moved — which is the whole of AC7, and is measured rather than asserted:
the test generates a config from a pre-F26 schema-1 binding and from a schema-2 all-defaults
binding and requires the resolved directories to be identical.

**A non-`file-system` store has no path at all** and generates `.` — so a Confluence-backed store
resolves to today's local directory and no artifact moves. What `knowledgebase_path` *should* mean
for a Confluence store is a filed open question
(`bug-knowledgebase-path-has-no-defined-meaning-for-a-confluence-store.md`) that Story 31.8-31.10
owns; this story does not answer it and deliberately does not change the value.

## 4. OQ-5 — research reports, as decided (not re-derived here)

**Decision (user, 2026-08-12): the three research reports belong to the SOFTWARE requirements
store.** Recorded here because AC4 requires the choice to be *recorded as a story-level decision
rather than invented as a requirement* — the PRD is silent, and this story does not add an FR.

- **Rationale on record.** FR264's legacy fields (`planning_artifacts`, `knowledgebase_path`)
  already resolve to the software store, so no existing project's research paths move and NFR82 is
  preserved with no exemption to argue.
- **Accepted trade-off.** Research is *not* stakeholder-visible when the system store is the
  Confluence-backed one. Deliberate, not an oversight.
- **Rejected: the system store.** Would need an explicit NFR82 exemption.
- **Rejected: split by research type.** Most accurate, but adds a third FR119 routing rule and
  would make the three bmad research skills route differently from each other.

Row 9-11's placement is pinned by test. It is not to be re-derived.

## 5. What consumes this table, and where routing actually happens

P2-10's rule holds: **path resolution happens inside the BMAD workflows, not in ma-agents code.**
ma-agents collects (31.5), persists (31.2), generates (31.3) and states the routing; the workflows
consume it. There are two consumption surfaces.

### 5.1 Upstream BMM workflows — via `project-context.md`

`bmad-prd`, `bmad-product-brief`, `bmad-architecture`, `bmad-ux`, `bmad-create-epics-and-stories`
and the three research skills ship in the upstream `bmad-method` package; this repository does not
vendor them. ma-agents reaches them through the surface it does own: every persona customization
in `lib/bmad-customize/*.customize.yaml` carries the critical action *"If
`_bmad-output/project-context.md` exists, read it completely"*, and
`generateRepoLayoutSection()` (`lib/installer.js`) writes the Repository Layout section that
document carries.

Those guidance sentences are defined once each, in `lib/installer.js`:

| Sentence | Artifacts it names | Emitted when |
| --- | --- | --- |
| `SYSTEM_STORE_GUIDANCE` | rows 1-4 | a two-store layout whose system store is elsewhere |
| `SOFTWARE_STORE_GUIDANCE` | rows 5-11 | a two-store layout whose software store is elsewhere |
| `LEGACY_KNOWLEDGEBASE_GUIDANCE` | the single-store wording, unchanged | a pre-31.5 single-store layout |

**Single-store projects still omit the section entirely** (P2-10, NFR34/NFR82) — the two-store
wording is an addition reachable only when a store actually moves, never a rewrite of what a legacy
project renders.

### 5.2 ma-agents' own skills — via `_bmad/bmm/config.yaml`

The skills in `skills/` and `lib/bmad-extension/skills/` that resolve a row of this table read the
generated `config.yaml` (FR264, AC5). Only **epics** (row 8) is resolved by an ma-agents-owned
skill; every one of those six entry documents already carries Story 31.4's binding preflight.

| Entry document | Row | Before | After |
| --- | --- | --- | --- |
| `skills/bmad-sprint-planning/SKILL.md` | 8 | `_bmad-output/planning-artifacts/` hardcoded | `{planning_artifacts}` from `config.yaml` |
| `skills/generate-backlog/SKILL.md` | 8 | `_bmad-output/planning-artifacts/epics.md` hardcoded | `{planning_artifacts}/epics.md` |
| `skills/prioritize-backlog/SKILL.md` | 8 | `_bmad-output/planning-artifacts/epics.md` hardcoded | `{planning_artifacts}/epics.md` |
| `lib/bmad-extension/skills/generate-backlog/SKILL.md` | 8 | `{sprint_management_path}/_bmad-output/planning-artifacts/epics.md` | `{planning_artifacts}/epics.md` |
| `lib/bmad-extension/skills/prioritize-backlog/SKILL.md` | 8 | `_bmad-output/planning-artifacts/epics.md` hardcoded | `{planning_artifacts}/epics.md` |
| `lib/bmad-extension/skills/bmad-sprint-planning/workflow.md` | 8 | already `{planning_artifacts}` | unchanged |

The fourth row is a **routing defect, not only an NFR37 one**: it resolved epics — a *software
requirements* artifact — through `sprint_management_path`, so a project whose sprint management and
software store diverge read its epics out of the wrong repository. AC2 and AC3 both forbid it.

## 6. Deliberately NOT routed by this story

Recorded so a reviewer sees a decision rather than an omission. Neither entry is an unassigned
*artifact type* — AC4's requirement is about the table above, which has none.

- **`{output_folder}`-only consumers: `sqa-audit`, `sqa-ieee12207`, `sqa-requirements-quality`.**
  They *read* the PRD, architecture and epics for audit purposes, from
  `{output_folder}/planning-artifacts/...`. They are not FR119 workflows (they neither create,
  edit nor validate those artifacts), and Story 31.4's OQ-3 answer **pins sqa-audit by name** as an
  `{output_folder}`-only consumer that must resolve no binding-derived field
  (`test/project-layout-staleness-guard.test.js:1745`, which names the file at `:1750`). Making
  them store-aware would move all
  three into the guarded set, requiring the preflight block to be added byte-identically to three
  more entry documents and their plugin mirrors, and would break that pin. **Deferred and
  reported**, not silently skipped: in a two-store project these three audit skills look for the
  PRD in the software store's directory. Worth a follow-up story.
- **MIL-498 document templates** (`OCD`, `SRS`, `SSS`, `SDD`, `SSDD`, `SDP`, `STD`). A separate
  document family under `{output_folder}/planning-artifacts/`, not an FR119 artifact type. Routing
  them would require deciding a system/software split for MIL-498 that no requirement states.

## 7. AC5 — the two negative rules

1. **No workflow reads `project-layout.yaml` for resolution.** The only place any skill entry
   document names that file is inside Story 31.4's `## Knowledge Store Binding Preflight` block,
   which is a read-only staleness check that resolves nothing. Enforced by scanning each entry
   document *with the preflight block removed*.
2. **No workflow hardcodes `_bmad-output/` as a relative-path assumption** for an artifact this
   table routes. Enforced for the row-8 documents above, outside the preflight block.

Rule 2 is scoped to artifacts this table routes. Sprint artifacts (rows 12-16) still spell
`_bmad-output/implementation-artifacts` in several sprint skills; AC3 requires those **unchanged**,
so this story does not touch them, and the pre-existing NFR37 exposure there is reported rather
than fixed under a story whose AC forbids the change.
