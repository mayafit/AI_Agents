# Withdrawn Requirements

> **Shard** of the [PRD index](../prd.md). Requirements listed here were withdrawn before
> implementation. Their IDs are never reused. The text is kept as written; it is not a
> specification of any ma-agents line. The 4.x line is specified in F29
> ([ma-agents-v7-line.md](capabilities/ma-agents-v7-line.md)); the 3.x line by the other

## Extension Decomposition & Thin Installer (bmad-method v6 extensions) — withdrawn

- FR268: ma-agents' skills, agents and workflows ship as **independent BMAD custom-source extension modules** — `ma-ops-agents` (SRE/DevOps/Cyber/SQA personas, their skill families, MIL-STD-498, Docker/cert skills, `bmad-dev-epic`), `ma-sprint` (sprint and backlog skills, file-system backend), `ma-atlassian` (Jira/Confluence overlay), `ma-knowledge` (Knowledge Atlas) and `ma-standards` (coding standards, git workflow, review, audit, test skills). Each module carries its own `module.yaml`, `module-help.csv` and `module_version`, and all are published from one repository through one `.claude-plugin/marketplace.json` listing one plugin per module, so the bmad-method installer's discovery mode offers them as a picker
- FR269: **Every extension installs and operates on an unmodified bmad-method install** via `npx bmad-method install --custom-source <git-url|local-path> --modules bmm --tools <ids>`, with the ma-agents npm package absent. Each module asks its own install-time questions through its `module.yaml` config prompts (e.g. Jira URL and project key, Confluence space and root page for `ma-atlassian`) rather than through the ma-agents wizard
- FR270: **No extension declares or requires another extension** at install time, and no skill in any extension references `ma-agents/bin/cli.js` or any other ma-agents package path. Where two extensions need the same guidance text (the tracker-routing block, the knowledge-store preflight), the text is **generated into each module from one canonical source at build time** and a prerelease gate fails on drift; it is never resolved across modules at run time. Runtime helpers an extension needs (binding stamp, Confluence page tree, publish-hook generation, Atlas engine) ship as scripts **inside** the owning skill and run via `uv run` or `node`
- FR272: `ma-sprint`'s skills are backend-agnostic: each exposes a **tracker hook point** (`[workflow] tracker = "file-system"` default plus an activation-prepend slot) instead of carrying the Jira branch inline. The Jira behaviour FR140 specifies is delivered once, as the `ma-atlassian` tracker adapter reference, and bound into each installed sprint skill by a generated `_bmad/custom/<skill>.toml` override. Removing `ma-atlassian` returns every sprint skill to file-system behaviour with no edit to the skill
- FR273: `ma-atlassian` is an **overlay**: its setup skill walks a **version-keyed target table** of upstream and ma-agents skills, generates an override for every target that is installed, skips absent ones, excludes every `v6-shims/` entry so no operation binds twice, and **reports by name every target or hook key it could not bind** rather than failing silently. At v6.12.4 the Jira targets are `bmad-sprint-planning`, `bmad-build`, `bmad-build-auto`, `bmad-code-review`, `bmad-correct-course`, `bmad-retrospective`, `bmad-walkthrough` and the `ma-sprint` skills; the Confluence targets are `bmad-prd`, `bmad-architecture`, `bmad-create-epics-and-stories`, `bmad-ux`, `bmad-product-brief`, `bmad-prfaq`, `bmad-spec`, `bmad-project-context`, `bmad-deep-recon`, `bmad-review`, `bmad-sprint-planning`, `bmad-build`, `bmad-build-auto`. The F26 deliverables (`bind`, `confluence-plan`, `confluence-record-root-page`, the binding stamp, the page tree, the publish-hook generator) are delivered by this module's in-skill scripts; their requirement text (FR254–FR267) is unchanged
- FR274: The `ma-agents` npm package is reduced to a **thin offline installer**: it carries the pinned `bmad-method`, the bundled module cache (FR75/FR123), **pinned copies of the five extension modules** vendored from a tagged release of the extension repository, the stage-and-invoke flow (P4-1, now passing multiple local `--custom-source` paths), IDE instruction-block injection, the on-prem profile and the Windows delete-retry. It performs no project-scoped work that an extension's own setup skill performs, and it no longer carries any skill content of its own or the custom-marketplace consumption feature (FR239–FR243 retired)
- NFR85: The extension repository versions **per module** (`module_version` in each `module.yaml`), not per repository; a change in one module never forces a version bump in another. The offline installer pins one repository tag and records which module versions it vendored

## BMAD v6.12.4 Integration — withdrawn

- FR275: The bmad-method pin is bumped from v6.10.0 to **v6.12.4** in one hop (supersedes FR236; v6.11.0 is not a stop). The bundled cache is rebuilt against the v6.12.4 registry pins (`tea` v1.27.2, `cis` v0.3.2, `bmb` current stable; `bmm` built-in) and the offline install is re-verified under `--network none`. A confirmation spike re-checks registry path/schema, the `--shims` flag semantics under `--yes` (so it can be **omitted** deliberately), the AGY `.agents/skills` collision and `removals.txt` handling on update, before downstream work
- FR276: ma-agents installs **without `--shims`**. The v6.12 catalog is adopted directly: `bmad-build` / `bmad-build-auto` replace `bmad-quick-dev` / `bmad-dev-story` / `bmad-dev-auto`; `bmad-walkthrough` replaces `bmad-checkpoint-preview`; `bmad-review` replaces the review/editorial family; `bmad-deep-recon` replaces the three research skills; `bmad-project-context` replaces `bmad-document-project`; `bmad-sprint-planning` absorbs `bmad-check-implementation-readiness` and `bmad-sprint-status`. ma-agents' own `bmad-dev-story`, `bmad-sprint-planning` and `bmad-sprint-status` are **deleted**; `bmad-dev-epic` is rewritten to orchestrate `bmad-build`, `bmad-build-auto`, `bmad-code-review`, `bmad-review` and `bmad-walkthrough`; every ma-agents-owned enumeration, "next steps" text, `module-help.csv` row, `MANIFEST.yaml` entry and training reference to a retired name (`bmad-create-story`, `bmad-dev-story`, `bmad-shard-doc`, `bmad-index-docs`, `bmad-agent-tech-writer`, `bmad-check-implementation-readiness`) is removed or repointed
- FR277: **`uv` and Python ≥ 3.11 are stated prerequisites** of every ma-agents install, including on-prem and air-gapped images, which must pre-seed `uv` and a matching interpreter so `uv run` never needs egress (re-asserts NFR2/NFR50/NFR57 with `uv` in the loop). ma-agents-owned skills that call the shared `_bmad/scripts/*.py` (`resolve_customization.py`, `resolve_config.py`, `memlog.py`) invoke them via **`uv run`**, matching upstream v6.11+. **Inverts FR213 and NFR74/NFR59(c)**; the former test guard ("no `uv run` in any ma-agents-owned skill") is replaced by its inverse for skill guidance, while control-plane JavaScript in the installer stays interpreter-independent
- FR278: Owned customization content is validated against the v6.12 contract before release: every owned `customize.toml` / generated `_bmad/custom/<skill>.toml` parses, references no undefined `{{.var}}`, states its own `persistent_facts` explicitly (upstream now ships them empty), and uses `{diff_file}` (not `{diff_output}`) in any review override. The `AGENTS.md` two-writer case (ma-agents' marker block + upstream `bmad-project-context`'s verified block) is covered by an integration test asserting neither writer clobbers the other's block or user prose
- FR279: ma-agents' `package.json` `engines.node` is raised to `>=20.12.0`; this is a user-visible compatibility change and is called out in the release notes

The 4.x counterparts: offline runtime FR282 and uv execution FR304 (FR277); contract validator FR303 and IDE injection ownership FR301 (FR278); installer surface FR298 (FR279); target commit FR280 (FR275); naming FR287 and epic orchestration FR292 (FR276); package map FR285–FR288 and FR295 (FR268–FR270); Jira store FR289 and sprint functions FR296 (FR272); Confluence overlay FR290–FR291 (FR273); installer FR298–FR299 (FR274); one version line NFR86 (NFR85).
