### BMAD v7 Target — pinned commit, GA gate, offline runtime (F27, 2026-11-07)

> Added 2026-11-07 by the Sprint Change Proposal of the same date (`sprint-change-proposal-2026-11-07.md`); Epic 36; Architecture Decision P5-11 (P5-11.5, P5-11.6). Upstream evidence: BMAD-METHOD `main` @ `e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6` (2026-11-06) — v7 preview alpha, GA announced for mid-November 2026, v6.12 frozen on branch `V6.12`. Supersedes the v6.12.4 thread below (FR275, FR276) for the v7 line; FR277–FR279 carry over unchanged. Placed above the v6.12.4 thread because this file is ordered newest first.

- FR280: **Target pin.** The pinned upstream commit (initially `e734d3ac3c0f4ea31cc2c2bbbe79e86e54f2cae6`) is the only bmad-method the v7 line is tested against; the Epic 36 gate records its verdict per SHA. The pin is recorded in `package.json` (`bmadRef`) and `BMAD_TARGET_REF` and is bumped deliberately (FR271)
- FR281: **GA qualification gate.** No on-prem (offline bundle) release of the v7 line until the Epic 36 gate has been re-run and passed on the v7 GA tag; until then ma-agents 3.18.x is the supported on-prem release. v7-based packages ship as a pre-release line until this gate passes
- FR282: **Offline runtime bundle.** The installer ships `uv`, a Python 3.11 interpreter and a wheelhouse covering every PEP 723 dependency declared by the vendored skills' scripts (enumerated at build; at least `jinja2`, `pyyaml`); an install under `--network none` must activate `render_skill.py`, `resolve_config.py`, `resolve_customization.py`, `tickets.py` and `setup.py` with `uv run --no-cache`. (A pre-seeded uv cache is not sufficient: `--no-cache` ignores it, so the offline path is a wheelhouse via `UV_FIND_LINKS` / `UV_OFFLINE`)
- FR283: **Skills CLI.** The installer vendors the `skills` npm package at a pinned version (1.7.6 at the pinned commit) and installs modules with `npx skills add <local path> --skill …` from the bundle; no network access is attempted
- FR284: **Headless setup.** The installer drives `bmad setup` non-interactively through `setup.py --module-answers <file>` with answers collected by its own wizard; if that contract changes upstream (it is an internal contract, not a documented CLI), the installer prints the exact `bmad setup <code>` instruction instead of failing (fail-loud, documented fallback)
