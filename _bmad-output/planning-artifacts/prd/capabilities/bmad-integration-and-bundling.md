## Functional Requirements

### BMAD-METHOD Integration

- FR8: Engineers can install the BMAD-METHOD framework alongside skills in a single workflow
- FR9: Engineers can update an existing BMAD installation to a newer version
- FR10: Engineers can apply organization-specific customizations to BMAD that persist across updates
- FR11: Engineers can register MIL-STD-498 workflows into an existing BMAD installation
- FR12: Engineers can trigger BMAD recompile after customization changes

### Bundled Installation

- FR74: The ma-agents npm package bundles bmad-method v6.3.0 as a direct dependency — no `npx` download at install time
- FR75: The ma-agents npm package bundles pre-cloned BMAD external modules (bmb, cis, tea) under `lib/bmad-cache/` — no git clone at install time. The two design-studio modules `gds` (Game Dev Studio) and `wds` (Whiteport Design Studio) are **not bundled**: they are absent from `lib/bmad-cache/` and from the cache manifest, and are therefore never pre-populated into `~/.bmad/cache/external-modules/` by FR76. Because bmad-method resolves an uncached module by `git clone --depth 1` against its upstream GitHub repository, **obtaining `gds` or `wds` requires network access, and on an air-gapped machine neither module can be installed**
- FR76: Before invoking bmad-method install, the installer pre-populates `~/.bmad/cache/external-modules/` from the bundled cache so bmad-method finds modules locally
- FR123: The ma-agents installer collects all BMAD-relevant configuration during its own interactive wizard — selected platforms/agents, user name, project path, module selections — and passes them to bmad-method as explicit CLI flags (`--tools`, `--modules`, `--directory`, `--user-name`, `--communication-language`, `--document-output-language`, `--output-folder`, `--custom-content`), rather than performing a silent install. For the `--modules` value, the default install set is **`bmm`, `tea`, `bmb`, `cis`**, drawn from the bundled cache manifest (`lib/bmad-cache/cache-manifest.json`). The optional-value `--bmad-modules` CLI flag overrides this default — bare (no value) opens a multiselect prompt; with a CSV (e.g. `--bmad-modules tea,bmb`) it installs exactly those. `bmm` is force-included in every path because the BMad core agents live there. The two design-studio modules `gds` (Game Dev Studio) and `wds` (Whiteport Design Studio) are **neither bundled nor installed** (FR75): they are not in the cache manifest, so the `--bmad-modules` multiselect **does not offer them** and `--bmad-modules gds` / `--bmad-modules wds` is rejected as an unknown module. A user who wants either module must obtain it over the network from its upstream GitHub repository; **on an air-gapped machine neither module is obtainable at all.** The air-gap coverage of NFR2/NFR50/NFR57 extends to the bundled set — `bmm` plus `tea`, `bmb`, `cis` — and the two design-studio modules are outside that guarantee. Experimental-channel modules (currently `automator`, `type: experimental`) and marketplace-plugin modules (currently `bmad-loop`) are filtered out of the **bundle** unconditionally. **Bundling and installing remain distinct concepts:** every bundled module ships in the offline cache so it can be installed without network access, and the bundled set and the default install set currently coincide. Epic 30's `KNOWN_BUNDLED_MODULES` allowlist (`{tea, bmb, cis}`) and its two-sided set-equality guard (NFR73) govern the **bundle** at cache-build time, computed on the resolved registry set; they are independent of the runtime *install* default.
- FR124: bmad-method performs its full configuration using the explicit parameters passed by ma-agents — the `--yes` flag suppresses prompts for parameters already supplied via flags, but does not skip configuration steps
- FR125: When bmad-method introduces new CLI parameters that ma-agents has not mapped, the `--yes` flag causes bmad-method to apply its own sensible defaults for those parameters — ensuring no configuration is missed even as bmad-method evolves
- FR126: The user experiences a single unified installation wizard — bmad-method runs non-interactively with full explicit parameters, with no separate BMAD interactive prompt appearing during the ma-agents installation flow
- FR127: In non-interactive mode (`--yes --force`), ma-agents uses its own defaults for all parameters and passes them to bmad-method via the same explicit flag mechanism — identical code path as interactive mode with pre-determined answers, ensuring CI/CD installations produce identical BMAD configuration as interactive ones

### Global Installation Scope (F26)

- FR248: The installation wizard **already asks an Installation Scope question** (`bin/cli.js:1414-1437`) offering project level, global (user-level settings), and custom path; `--global` is its non-interactive equivalent. That question is retained as-is. What F26 changes is the **consequence** of choosing global: BMAD is no longer silently dropped (FR249), and the chosen scope is recorded so a later `ma-agents bind` (FR252) knows the install was global. **[AMENDED 2026-08-02 — originally written as though the interactive question did not exist and had to be built. Source verification showed it already ships; the requirement is narrowed to the behaviour change only, and Story 31.11 shrinks accordingly.]**
- FR249: When global scope is selected, BMAD modules and BMAD agents are installed globally alongside ma-agents skills — superseding the current behaviour where BMAD agents are filtered out of global installs and the user is told to re-run without `--global`. The set of BMAD modules installed globally is the same default set FR123 defines for project installs
- FR250: Global installation is **spike-gated**. Before FR249 is implemented, a confirmation spike establishes what bmad-method v6.10.0 actually supports for user-level installation — target directory, whether `--directory` accepts a user-scoped path, and how module resolution behaves outside a project. If the spike shows global BMAD install is unsupported upstream, FR249 degrades to installing ma-agents skills globally and the installer reports three things: that BMAD remains project-scoped, the command that installs BMAD into a project, and that the F26 knowledge-store requirements are unaffected. The remaining F26 requirements proceed unchanged
- FR251: A global install performs **no project-scoped work** — it does not generate `project-context.md`, does not write `project-layout.yaml`, and does not prompt for knowledge-store locations, because no project is in scope at that moment. These are deferred to the per-project bind step (FR252)
- FR252: A **project-bind step** (`ma-agents bind`, also offered automatically when a globally-installed skill activates in a project that has no `_bmad-output/project-layout.yaml`) collects only the project-scoped answers — the two knowledge-store bindings (FR254) and sprint management location — and writes `_bmad-output/project-layout.yaml` plus `project-context.md`. It installs no skills and no BMAD modules; its re-run behaviour is governed by NFR78
- FR253: `ma-agents status` reports the active install scope, and for a global install lists which projects on this machine have been bound, and for each whether a readable `project-layout.yaml` was found at its root

### BMAD Extension Architecture

- FR104: The BMAD extension module is restructured with a proper BMAD 6.2.0 `module.yaml` containing `code` (module identifier), `description`, and `module_version` fields — replacing the legacy `extends-module: bmm` pattern in the current `lib/bmad-extension/module.yaml`
- FR105: A module setup skill is created that writes module configuration to `config.yaml` (shared, git-committed), `config.user.yaml` (personal, gitignored), and `module-help.csv` (capability registry) — following the BMAD 6.2.0 anti-zombie pattern where re-running setup removes all existing entries for the module's code before writing new values
- FR106: The dual-layer agent definition pattern — base config in `lib/bmad-customizations/bmm-{agent}.customize.yaml` + extended config in `lib/bmad-extension/agents/bmm-{agent}.customize.yaml` — is consolidated into a single authoritative agent skill folder per agent under the module's `agents/` directory

### Extension Decomposition & Thin Installer (F28)

> Added 2026-10-31 by the Sprint Change Proposal of the same date (Architecture Decision P5-10). **Amends F4:** FR104–FR106 described ONE extension module (`ma-skills`); from P5-10 ma-agents ships N independent extension modules from one marketplace repository and the npm package becomes a thin offline packaging of them. FR104–FR106 remain true *per module*.

- FR268: ma-agents' skills, agents and workflows ship as **independent BMAD custom-source extension modules** — `ma-ops-agents` (SRE/DevOps/Cyber/SQA personas, their skill families, MIL-STD-498, Docker/cert skills, `bmad-dev-epic`), `ma-sprint` (sprint and backlog skills, file-system backend), `ma-atlassian` (Jira/Confluence overlay), `ma-knowledge` (Knowledge Atlas) and `ma-standards` (coding standards, git workflow, review, audit, test skills). Each module carries its own `module.yaml`, `module-help.csv` and `module_version`, and all are published from one repository through one `.claude-plugin/marketplace.json` listing one plugin per module, so the bmad-method installer's discovery mode offers them as a picker
- FR269: **Every extension installs and operates on an unmodified bmad-method install** via `npx bmad-method install --custom-source <git-url|local-path> --modules bmm --tools <ids>`, with the ma-agents npm package absent. Each module asks its own install-time questions through its `module.yaml` config prompts (e.g. Jira URL and project key, Confluence space and root page for `ma-atlassian`) rather than through the ma-agents wizard
- FR270: **No extension declares or requires another extension** at install time, and no skill in any extension references `ma-agents/bin/cli.js` or any other ma-agents package path. Where two extensions need the same guidance text (the tracker-routing block, the knowledge-store preflight), the text is **generated into each module from one canonical source at build time** and a prerelease gate fails on drift; it is never resolved across modules at run time. Runtime helpers an extension needs (binding stamp, Confluence page tree, publish-hook generation, Atlas engine) ship as scripts **inside** the owning skill and run via `uv run` or `node`
- FR271: ma-agents targets **exactly one bmad-method version — the latest the team has qualified** (v6.12.4 at adoption) — and never installs or maintains upstream `v6-shims/`. When upstream retires a workflow in favour of a successor, ma-agents binds and orchestrates the successor only (e.g. `bmad-build` / `bmad-build-auto` in place of `bmad-create-story` / `bmad-dev-story`); ma-agents-owned skills that shadowed an upstream name (`bmad-dev-story`, `bmad-sprint-planning`, `bmad-sprint-status`) are removed in favour of the upstream skill plus overlay. Supersedes the shim-transition option in `bmad-6.11-6.12-impact-analysis.md` §7
- FR272: `ma-sprint`'s skills are backend-agnostic: each exposes a **tracker hook point** (`[workflow] tracker = "file-system"` default plus an activation-prepend slot) instead of carrying the Jira branch inline. The Jira behaviour FR140 specifies is delivered once, as the `ma-atlassian` tracker adapter reference, and bound into each installed sprint skill by a generated `_bmad/custom/<skill>.toml` override. Removing `ma-atlassian` returns every sprint skill to file-system behaviour with no edit to the skill
- FR273: `ma-atlassian` is an **overlay**: its setup skill walks a **version-keyed target table** of upstream and ma-agents skills, generates an override for every target that is installed, skips absent ones, excludes every `v6-shims/` entry so no operation binds twice, and **reports by name every target or hook key it could not bind** rather than failing silently. At v6.12.4 the Jira targets are `bmad-sprint-planning`, `bmad-build`, `bmad-build-auto`, `bmad-code-review`, `bmad-correct-course`, `bmad-retrospective`, `bmad-walkthrough` and the `ma-sprint` skills; the Confluence targets are `bmad-prd`, `bmad-architecture`, `bmad-create-epics-and-stories`, `bmad-ux`, `bmad-product-brief`, `bmad-prfaq`, `bmad-spec`, `bmad-project-context`, `bmad-deep-recon`, `bmad-review`. The F26 deliverables (`bind`, `confluence-plan`, `confluence-record-root-page`, the binding stamp, the page tree, the publish-hook generator) are delivered by this module's in-skill scripts; their requirement text (FR254–FR267) is unchanged
- FR274: The `ma-agents` npm package is reduced to a **thin offline installer**: it carries the pinned `bmad-method`, the bundled module cache (FR75/FR123), **pinned copies of the five extension modules** vendored from a tagged release of the extension repository, the stage-and-invoke flow (P4-1, now passing multiple local `--custom-source` paths), IDE instruction-block injection, the on-prem profile and the Windows delete-retry. It performs no project-scoped work that an extension's own setup skill performs, and it no longer carries any skill content of its own or the custom-marketplace consumption feature (FR239–FR243 retired)

## Quality Attributes (Non-Functional Requirements)

### Global Installation Scope (F26)

- NFR76: Choosing project-level scope must not change project-level install behaviour beyond what F26 itself introduces, and must add no additional prompts on subsequent runs. The comparison baseline is **post-FR263 behaviour**, not today's: a project install will now always write `_bmad-output/project-layout.yaml`, which today it does not write at all in single-repo mode and in fact deletes (`bin/cli.js:606-616`). Against that rebaselined output the install must be deterministic. **[AMENDED 2026-08-02 — the original 'byte-identical to today's' wording became unachievable the moment FR263 made project-layout.yaml unconditional; rebaselined rather than weakened.]**
- NFR77: Global installation must work fully air-gapped, on the same terms as project installation — bundled BMAD cache, no npm/git/CDN access at install time (re-asserts NFR2/NFR50/NFR57)
- NFR78: The project-bind step must be idempotent and non-destructive — re-running it against an already-bound project reports the existing bindings and changes nothing unless the user explicitly edits an answer, and it never overwrites an existing `project-context.md` (consistent with NFR23)

### BMAD Extension Compatibility

- NFR16: The BMAD extension module must survive `npx bmad-method install --action update` without losing functionality — extensions maintain independent identity and persist across BMAD updates
- NFR17: All BMAD-facing changes must use official BMAD Builder extension APIs only — `module.yaml` (module identity), `module-help.csv` (capability registration), setup skill (config management), Agent Builder (agent creation), Workflow Builder (workflow creation), skill folder standard (SKILL.md + prompts/ + resources/ + scripts/) — zero bmad-method core modifications
- NFR18: OpenCode JSON instruction injection must not corrupt existing `opencode.json` configuration — JSON config merging must be additive-only
- NFR19: Bug and sprint extension workflows must function identically whether invoked via BMAD agent menu or direct slash command. All sprint workflows must read/write the unified `sprint-status.yaml` file — no workflow may create or depend on separate `backlog.yaml` or per-sprint YAML files
- NFR84: **Independent installability is tested per module** — the extension-contract tests (marketplace/manifest enumeration, deterministic build and drift gate, offline PluginResolver passthrough) run for each module in isolation against the pinned bmad-method, and a release gate installs each module alone on a clean machine with no ma-agents package present. Skill directory names must be unique across all modules (IDE skill folders are flat; bmad-method ≥ 6.10.0 aborts on duplicate leaf names)
- NFR85: The extension repository versions **per module** (`module_version` in each `module.yaml`), not per repository; a change in one module never forces a version bump in another. The offline installer pins one repository tag and records which module versions it vendored

### Bundled Installation

- NFR20: The bundled BMAD cache must be version-pinned (v6.3.0 current) — upgrading the bundled version is a deliberate, tested release operation, not an automatic fetch
- NFR21: The bundled installation produces deterministic `_bmad/` output from the included cache. The resulting directory structure is reproducible given the same ma-agents package version.
