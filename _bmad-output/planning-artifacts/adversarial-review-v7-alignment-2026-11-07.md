## v7 facts this review relies on

A source can be "a local folder, or a repository at a tag" (`docs/customize/add-modules.md`). `npx bmad-method install --custom-source` is documented only as the v6.12 path (same file, "Modules in v6.12").
- A module is a `bmod-<code>` record (`bmod.toml` `[bmod]` with code/version/update_source/skills/required_skills/recommended_skills/`[[bmod.config_questions]]`, plus `help/help.md`, `roster.toml`, `retired.toml`, `migration-<n>.toml`). "Headless and inline-argument setup: Removed". "Reads of `user_name`, `communication_language`, and `document_output_language` are removed". `marketplace.json`: "The current install path does not need it" (`docs/toolsmith/migrate-an-old-module.md`).

It maps only statuses and `action_items`, then moves `sprint-status.yaml` to `archive-v6/` unchanged. "Sofia … replaces `bmad-sprint-planning`, `bmad-create-epics-and-stories`, `bmad-ticket`, `bmad-spec` and `bmad-correct-course`" (`skills/bmod-method/migration-1.toml`).

"Hooks are not integrated yet, so nothing syncs on its own" (`skills/bmad-agent-po/config/jira-ticketing.toml`, `skills/bmad-agent-po/references/store-setup.md`, `docs/plan/set-up-the-ticket-tree.md`).

## Findings

- **The plan never mentions v7.** A `git grep -i v7` over the proposal, the PRD F27/F28 shards, P5-10, Epics 32–35, the readiness report and Stories 32.1–32.9 finds only three pre-existing lines about the `bmad-create-architecture` shim. FR271 (`bmad-integration-and-bundling.md:58`) and P5-10.5 make "the latest the team has qualified" the policy, and FR275 pins v6.12.4. Upstream says v6.12 is frozen and v7 lands mid-November (`docs/start/install-bmad.md`). As written, latest-only either strands ma-agents on a frozen branch the policy says it must leave, or forces an unbudgeted v7 epic within weeks of Epic 32's release gate. Change now: add a v7 qualification requirement and decision (trigger, gate spike, which of Epics 33–35 are paused until it lands), and restate FR271 as "v6.12.4 until v7 GA is qualified".
- **Epic 33's whole delivery vehicle is v6-only.** FR268 (`:55`), FR269 (`:56`), P5-10.2, NFR84 and Epic 33.1/33.5 define the extension repository as `.claude-plugin/marketplace.json` → N plugins, a `module.yaml` + `module-help.csv` per module, PluginResolver passthrough tests, and `npx bmad-method install --custom-source … --yes` as the release-gate command. v7 has none of these: `marketplace.json` "is not needed" (`migrate-an-old-module.md`), there is no `bmad-method` installer or PluginResolver, and a `module.yaml` module "does not work with `bmad setup`". Every Epic 33 artefact (marketplace template, `scripts/build.js` digests, the per-module drift gate, the passthrough test, the 33.5 gate) is rebuilt at the v7 move, and a `bmod.toml` / `help/help.md` / `roster.toml` / `retired.toml` set is authored from scratch. Change now: scaffold 33.1 in the v7 layout (`skills/bmod-<code>/bmod.toml`, member `[skill]` tables, `help/help.md`). Treat `module.yaml` + `marketplace.json` as a generated v6 compatibility output for as long as 6.12.4 is supported, not as the source of truth.
- **The thin installer has nothing to stage or invoke under v7.** FR274 (`:61`), P5-10.1 and Epic 35 (35.1 `stagePlugin()` with N local `--custom-source` paths; 35.4 byte-identical `_bmad/<module>/` trees) all assume a pinned `bmad-method` npm package that runs non-interactively with flags (FR123–FR127). In v7 there is no such package. Install is `npx skills add` from a local folder or a tag. Configuration is `bmad setup <code>`, driven by the agent, with "neither" headless nor inline-argument setup. The only scripted path is `setup.py --module-answers <file>` (`skills/bmad/references/setup.md`), which is an internal contract. `build-bmad-cache.js`'s npm-tarball and tea/cis/bmb clones also have no direct v7 counterpart: bmb becomes `bmod-toolsmith` inside BMAD-METHOD. No story says what the v7 offline bundle holds. It would need a BMAD-METHOD skills snapshot, the `skills` CLI npm package, `uv` + Python, PEP 723 wheels, and a `file:` `update_source`. Change now: keep Epic 35 out of execution until v7 ships, and re-scope it as "vendor sources for `npx skills add <local path>` + seed `uv`/wheels + optionally drive `setup.py`". Do not build N-path `--custom-source` staging that will be deleted.
- **The air-gap mitigation is defeated by v7's own `uv run --no-cache`.** P5-10.6, FR277 (`bmad-platform-currency.md:30`) and Story 32.1 AC4 / Dev Notes prove offline `uv` by pre-seeding `UV_CACHE_DIR` and an interpreter, and test only `resolve_customization.py` / `resolve_config.py`, which have no dependencies. On v7 main, every skill entry point is `uv run --no-cache … render_skill.py` (`skills/bmad-build/SKILL.md`, `skills/bmad-agent-po/SKILL.md`). `--no-cache` makes `uv` use a temporary cache, so a pre-seeded cache is not read. `render_skill.py` declares `jinja2>=3.1`, and `tickets.py` declares `pyyaml`. A v7 air-gapped install therefore needs a local wheelhouse or an on-prem index (`UV_FIND_LINKS` / `UV_INDEX_URL`), not a warm cache, and the 32.1 PASS criterion does not transfer. Change now: make 32.1 AC4 and 32.9 AC1 exercise `render_skill.py` with `--no-cache`, and record a wheelhouse-based seeding recipe, so the on-prem image spec survives the v7 move.
- **`ma-sprint` is built on a file v7 stops reading, and the plan invests in it.** P5-10.1, FR272 (`:59`), the P2-11 amendment, NFR19 ("All sprint workflows must read/write the unified `sprint-status.yaml`", `:76`) and Epic 34.2 give eleven skills hook points around `sprint-status.yaml` (epics/backlog/sprints sections). v7 has no sprint-status file, no sprint-planning skill and no sprint concept. `migration-1.toml` maps only story statuses and `action_items` into `tickets.toml` / plans, and moves `sprint-status.yaml`, with our `backlog:` and `sprints:` sections, to `archive-v6/` unchanged. Every Epic 34 hook point, stub and test on these skills is redone or discarded at v7, and existing users' sprint capacity data is archived, not migrated. Change now: name the v7 shape of `ma-sprint` before Epic 34 starts, either as a thin layer over `tickets.toml` (sprint membership as a field or label read through `tickets.py`), or as retired in favour of Sofia's BOARD. Add a `migration-<n>.toml` requirement for the `sprints:` / `backlog:` sections that upstream's migration drops.

## Where the plan is already aligned

- Dropping `--shims` and never binding a `v6-shims/` name (FR271, P5-10.5) matches v7, which has no shims and treats `core/v6-shims` / `bmm/v6-shims` as legacy leftovers to delete (`migrate_v6.py:62-74`).
- `uv` + Python ≥ 3.11 as a hard prerequisite and `uv run` for shared scripts (FR277, P5-10.6) matches v7. Every shipped script declares `requires-python = ">=3.11"`, and `uv` is "REQUIRED" (`bmod-core-tools/bmod.toml` `pre_install_message`).
- The `_bmad/custom/<skill>.toml` team-override layer as the only way to reach into another skill (P5-10.4) is the surface v7 keeps and documents. `bmad setup` moves custom files on renames and "never changes a value inside a file", so marker-delimited overrides survive setup refreshes.
- FR278 / Story 32.7 (explicit `persistent_facts`, `{diff_file}` in review overrides, parse validation) matches the v7 `customize.toml` contract verbatim (`skills/bmad-build/customize.toml`).
- Retargeting `bmad-dev-epic` onto `bmad-build-auto` / `bmad-code-review` / `bmad-review` / `bmad-walkthrough` (32.5 AC3) picks skills that all exist on v7 main, so the pipeline half of the rewrite carries forward.

## Reviewer's closing note

The plan is not v7-aligned as a whole. Its principles carry over: latest-only, no shims, `uv`, the customization layer, independent modules, deleting shadow skills. Its concrete deliverables do not, because almost all of them are expressed in v6.12 mechanics. The marketplace/`module.yaml` repository (Epic 33), the `sprint-status.yaml`-centred `ma-sprint` and the prepend-everywhere Jira adapter (Epic 34), the `--custom-source` staging installer (Epic 35), and the `_bmad/bmm/config.yaml` binding spine all hit something v7 removes or replaces. Executed as written, the v7 move would rework every one of the five extensions and the installer, which is far from minimal. The single change that would most reduce the v7 migration cost is to gate Epics 33–35 on v7 GA, and to author the carved modules in the v7 bmod layout from the first commit (`bmod.toml`, `help/help.md`, `roster.toml`, code-prefixed names, `resolve_config.py` reads), generating the v6.12.4 `module.yaml` / `marketplace.json` as a temporary compatibility output rather than the other way round.
