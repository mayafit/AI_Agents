## Specification gaps (what a builder cannot find in the set)

- **Skill-by-skill module inventory.** P5-11.1 lists families and wildcards. Of the skills that exist today, these are assigned to no package: `ai-audit-trail`, `document-revision-history`, `test-accompanied-development`, `code-documentation`, `cmake-best-practices`, `vercel-react-best-practices` (`skills/`), and possibly `create-hardened-docker-skill` / `verify-hardened-docker-skill` / `docker-image-signing` / `docker-hardening-verification` under the vague "docker/cert". `bmad-knowledge` exists in both `skills/` and `lib/bmad-extension/skills/`. `ma-knowledge` is "single- or multi-skill module", which is undecided. `confluence-plan` and `confluence-record-root-page` are listed as skills but exist today only as CLI commands, and no SKILL.md contract (inputs, outputs, scripts) is specified for them. A complete table (skill → module → new name → `retired.toml` entry) is needed.
- **Fate of the twelve `ma-sprint` skills for v7 users.** The spec says only "not carved; stay in the 3.x monolith". It does not say what an upgrading 3.x user loses when the installer's `uninstall` removes the `ma-skills` module (FR294). It does not map `my-next-issue`, `create-bug-story` and `story-status-lookup` to Sofia verbs, or say whether the installer warns about them. It does not say what `auto-bug-detection` (in `ma-standards`, which today calls `story-status-lookup` / `create-bug-story`) does in v7.
- **How a user adds a third-party or organisation module.** FR274 retires FR239–FR243 with no positive replacement. FR246 still tells Demerzel users to install its replacement "via the custom marketplace source (FR239–FR243)", which no longer exists. The offline installer's support for an organisation-local module (a `file:` path or an on-prem Git host) is unspecified.
- **Installer wizard and CLI surface for v7.** No requirement lists the questions the thin installer asks, its flags, its non-interactive mode (the FR127 equivalent) or its answers-file format. No requirement maps `lib/agents.js` platform IDs to Skills CLI agent targets, or says which modules are selected by default (the FR123 equivalent). It is also unspecified whether install scope (F26 FR248–FR253, global vs project) exists in the v7 line, given that the Skills CLI has its own global mode.
- **Bundle contents and default install set.** The structure tree says "BMAD-METHOD `skills/` snapshot … (+ tea / cis module repos at their tags)". Story 36.3 says "bmb is replaced by `bmod-toolsmith`". No requirement states which upstream modules (core, method, toolsmith, tea, cis, …) are bundled and which are installed by default, the supported wheelhouse platforms (36.2 AC2 leaves macOS to "if the PO names it"), the bundle manifest schema, or a size budget.
- **v7 configuration model per module.** The `ma-atlassian` keys are named (`jira_site` … `confluence_mcp_server`), but their types, defaults, scope (`user` vs team, which 36.1 AC5 shows the setup contract distinguishes), validation and credential handling are not. F26's two-store model (system vs software requirements store, FR254) has no v7 statement: the key list has one `confluence_space` and one `confluence_root_page`, and the spec never says whether the two-store distinction is dropped. `ma-ops` declares "none" while `ma-ops-dev-epic` has model tiers and publish settings, and the spec does not say whether these are `customize.toml` defaults or config questions.
- **Bind target table.** FR290 and P5-11.4 give a partial target list and delegate the (skill, section, key, insertion slot) table to Story 36.1. The `override-targets.toml` content, the role per target (publish vs read), the marker format and the `status` output of `ma-atlassian-bind` are not specified.
- **Migration specifications.** `bmod-ma-ops/migration-1.toml` and `bmod-ma-atlassian/migration-1.toml` are described in one sentence each. Missing: the exact inputs (which 3.x files and keys), outputs (which store files, which `_bmad/custom` files, which setup answers), ordering relative to `bmad migrate method`, idempotence, behaviour on a partially migrated project, the conflict rule for id collisions (36.1 AC9 anticipates them), and the report format.
- **Help and roster content.** FR286 requires `help/help.md` and an "ops" roster group, but specifies no help content, structure or roster fields (persona, icon, menu) beyond names.
- **IDE parity in v7.** NFR52 (multi-tool parity) and FR209/FR210 (Cline workflow wrappers) are written for `bmad-method --tools`. No v7 requirement says which IDE targets must work, how Cline `.clinerules/workflows/` wrappers are produced for Skills-CLI-installed skills, or which tests prove it.
- **Test gates as requirements.** NFR84 (am.) covers per-module CI. There is no v7 NFR for the offline installer gate (NFR50 still says "bundled plugin install flow"), the 3.x → v7 upgrade gate, or the GA re-qualification gate's pass criteria. These exist only as story ACs (36.6, 36.7, 39.5).
- **Versioning and release mapping.** The starting version of the `ma-bmad-extensions` version line is unspecified, as are how an installer version (4.0.0) maps to an extension tag and an upstream SHA, the pre-release version string (36.6 AC7 leaves it to the PO), and how `bmad status` reports an offline-installed module.
- **Installer `status` and `uninstall` behaviour in v7.** These are named in P5-11.1 and Epic 39, with no requirement stating what they report or remove for a v7 install, beyond "removes the v6 `ma-skills` module".
- **Prerequisites for online (non-installer) users.** FR277 states uv and Python 3.11. Node ≥ 20.12 is needed for the Skills CLI and for the JavaScript skill scripts (`atlas.cjs`, the Confluence engine), but that is stated only in a rejected-alternatives paragraph and in FR279 (which concerns the installer's own `engines`), not as a module prerequisite.

## Proposed document structure

- **PRD (specification).** Add one capability file for the next product, e.g. `prd/capabilities/ma-agents-v7-modules-and-installer.md`. It contains only live F27/F28 requirements as plain statements: package map, per-module contents and config, installer, offline runtime, bind, migrations, gates. Renumbering is not needed, but no FR carries an amendment bracket. The PRD index gains a "Product lines" section (the single 3.x constraint) and a machine-readable requirement status register (ID, status `live`/`superseded`/`retired`/`3.x-only`, replaced-by). That register is the only place supersession appears. v6-era threads (F5/F20/F21/F23/F24/F25, the v6.12.4 thread, NFR16/17/20/21 in their v6 form) move to `prd/archive/3x-line.md`, unchanged.
- **Architecture (specification).** P5-11 is rewritten as a self-contained decision whose Context states v7 platform facts and product constraints. Its alternatives are real design options, without epic numbers. P5-10 and the P2-11 amendment move unchanged to `architecture/archive/`. `structure-and-boundaries.md` gets one v7 target tree plus v7 boundary, data-flow and FR-mapping tables. The 3.x layout sits under a "3.x line" heading. `implementation-patterns.md` gets repository-scoped v7 rules, and the P5-10 block is removed.
- **Epics and stories (plan, specification-adjacent).** Epics 32–35 move unchanged to `epics-archive.md` (or are left only in SCP 2026-10-31), which satisfies the convention that cancelled or completed epics are kept as history and not edited. Epics 36–39 trace to FR/decision IDs, not SCP sections. Story Context sections state current facts, not predecessors. 3.x coexistence ACs are a separate labelled block. The two lifecycle tags become one "Re-run at GA" field.
- **Records (history).** `sprint-change-proposal-2026-10-31.md`, `sprint-change-proposal-2026-11-07.md`, the adversarial reviews, the readiness reports, `prd/changelog.md` and an architecture changelog hold all "amended / superseded / was / never executed / corrected" text. `sprint-status.yaml` comments hold current status and blockers only, and `last_updated` is a date.

## Reviewer's closing note

The v7 design is mostly present, but it is buried. Nearly every live statement reaches the reader as an amendment bracket, a supersession banner, or a contrast with a plan that was never built. A builder working only from these documents would have to reconstruct the October plan to understand what the November plan removes, which is the reverse of what a specification is for. The narrative also hides real gaps: unassigned skills, no positive replacement for the custom-source feature, no v7 installer surface, an undecided owner for IDE injection, and migrations described in a sentence. Fixing the structure (one live v7 capability file, one product-lines statement, archives for P5-10 and Epics 32–35) will expose those gaps quickly. They need to be closed before Epic 37 starts carving.
