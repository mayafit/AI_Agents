BMAD Knowledge Atlas

The human-facing visualization tier of the BMAD Knowledge Graph: a pre-bundled, fully offline static-site generator that turns any project's _bmad-output into an interconnected, navigable, analyst-grade knowledge site — generated on demand, sealed for air-gapped on-prem networks.

Decision P5-7 · extends P3-1 Covers FR215–FR234 · NFR60–NFR69 Scope v1 = deterministic core Basis PRD · brief + addendum · brainstorming

The headline

You have a graph backbone — this adds the map you travel

P3-1 gave BMAD a knowledge-graph data model (knowledge-graph.json) and a single graph renderer (open-graph). But it is populated only by forward skill emission — blind to brownfield knowledge, version upgrades, and edits made outside any skill — and it renders one generic graph, not a site. The Atlas closes both gaps: an authoritative scan that sees everything on disk, distilled into a manifest, rendered as a cross-linked, multi-view, searchable knowledge site — and it stays a strict superset of the P3-1 model, not a fork.

Everything is generated offline from a pre-bundled engine. No server to view, no per-project install, no network at any point — the same self-containment discipline as the bundled BMAD cache (P2-6).

01 — Pipeline

How a folder of markdown becomes a knowledge site

One pre-built engine, invoked by the bmad-knowledge skill. The order is load-bearing — note step 3, the manifest, which is the seam the whole design pivots on.

  1. 1
    Authoritative scan bmad-knowledge skill

    Enumerate every document under _bmad-output (planning + implementation + project-context), tolerant of missing types. A scan is authoritative — not an event hook — so brownfield, upgraded, and out-of-band-edited knowledge is all seen (FR216).

  2. 2
    Parse & extract entities deterministic

    Frontmatter + body parsed for the stable BMAD vocabulary — FR###, NFR##, F##, Epic N, Story N.M, bug-*, P#-#, retros, statuses (FR218). ~90% of the graph, free and reproducible.

  3. 3
    Build manifest the seam — single source of truth

    Typed nodes + edges on the P3-1 file-id#anchor identity, per-file content hashes, entities, edges. The manifest is a superset of knowledge-graph.json; when that file is present it is read and reconciled (FR221, FR232, FR228).

  4. 4
    Cross-link + backlinks pure transform

    Every entity token anywhere becomes a hyperlink to its canonical location; each entity gets its "referenced by" backlinks (FR219, FR220).

  5. 5
    Generate diagrams HTML/CSS/SVG

    Where none are authored, draw them — the FR→Epic→Story→Bug→Retro traceability spine, epic→story trees, sprint/status board (FR224).

  6. 6
    Render self-contained site _bmad-output/knowledge-site/

    Reading views, typed force-graph home, orphan/gap view, offline search, health snapshot — all assets embedded locally, graph data as a JS variable (never fetched). Open index.html; no server (FR222–FR227, FR229).

02 — The seam

The manifest splits the engine in two — and that solves air-gap

Discovery may want a model (later, for enrichment); rendering must never need one. The manifest is the contract between them: write it on one side, read it on the other.

Discovery half
scan · parse · graph-build
  • Runs at skill-invocation time
  • Model may be present (enrichment is a deferred tier)
  • Output: the manifest
manifest.json
⇄
the contract
Rendering half
cross-link · diagrams · render
  • Pure, model-free, no network
  • Reads only the manifest
  • Output: the static site
Why it mattersThe renderer's independence from any model or network is what makes a beautiful site and an air-gapped site the same deliverable. The manifest also doubles as the diff anchor (content-hash incremental rebuilds) and as the P3-1 graph data.

03 — Invariants

The calls everything built from this must share

The durable decisions — what a future builder can't safely read off the code. Each names the divergence it prevents.

Authoritative scan, not hooks

Correctness comes from a full scan of on-disk artifacts; hooks are at most optional sugar that re-invoke the scan.Prevents — a stale site after upgrades / brownfield / out-of-band edits.

Manifest = single source of truth & superset of knowledge-graph.json

Shared file-id#anchor identity (P3-1); manifest nodes/edges are schema-compatible.Prevents — two divergent graph models; identity drift from emitToGraph.

Discovery↔rendering contract

The renderer consumes only the manifest and runs with no model and no network.Prevents — coupling render quality to model availability; an air-gap break at view time.

Sealed offline packaging

Engine + every generate/view dependency ship pre-built/vendored in the ma-agents distribution; no per-project npm install.Prevents — any npm / git / CDN / host need on a disconnected network (NFR67; offline-install gate extended).

Zero-dependency-first rendering

Curated views = self-contained HTML/CSS/SVG; force-graph + Mermaid bundled only where needed; graph data embedded, never fetched.Prevents — a heavy/fragile bundle and the blank-screen failure mode (FR234 progressive enhancement).

Non-destructive, isolated output

All output to a git-ignorable _bmad-output/knowledge-site/; sources never mutated.Prevents — the Atlas corrupting the knowledge it reads.

Deterministic, cross-platform incremental build

Content-hash change detection (mtime only a pre-filter); Windows path + CRLF safe; identical inputs → identical output.Prevents — false diffs across git checkout/pull; platform-dependent output.

04 — Sealed offline

Two dependency surfaces, both sealed

"Works on a disconnected on-prem network, all packages installed as part of ma-agents" means closing both surfaces — the generated site and the engine that makes it.

SurfaceWhat shipsGuarantee
View-time

Install + generate-time

Verified, not assertedThe existing offline-install gate is extended to exercise Atlas generation and viewing with all egress blocked — re-asserting the air-gap guarantee of P2-6 / NFR2 / NFR50 / NFR54 / NFR57 for this new surface.

05 — Composition with Epic 19

It composes with emitToGraph, it doesn't replace it

Stories 19-1…19-4 build the write path (skills emit nodes/edges as they produce artifacts). The Atlas scan is the backfill + render path. Two halves of one model.

// write path (Epic 19) — skills emit as they run
create-prd, create-architecture, create-story, dev-story  → emitToGraph()  → knowledge-graph.json

// backfill + render path (P5-7) — on-demand scan
bmad-knowledge  → scan(_bmad-output)  → manifest  ⊇  knowledge-graph.json
                → reconcile (union on file-id#anchor; scan wins for on-disk truth)
                → render knowledge-site/

// when knowledge-graph.json is ABSENT (today): scan alone produces an equivalent manifest
Recommended build order

Atlas-first

Ship scan + manifest + render first — it delivers value standalone, with or without Epic 19. Then wire knowledge-graph.json ingestion as a reconciliation fast-follow once 19-x lands.

[ASSUMPTION] to ratify

Sequencing in epics

Exact ordering vs. stories 19-1…19-4 is confirmed in epic/story planning — captured as an open item, not silently decided here.

06 — Scope

What v1 ships, and what waits

v1 — deterministic core
  • Scan → manifest → generate + open self-contained site
  • Entity auto-linking + backlinks; typed force-graph nav
  • Reading views + rendered/auto-generated diagrams
  • Orphan/gap detection; offline search; health home
  • Content-hash incremental rebuild
  • Pre-bundled, sealed-offline engine
Deferred tiers
  • Model-assisted enrichment (brownfield classification, prose relationships, AI summaries) — the narrative layer
  • Auto-refresh BMAD-skill hooks (optional sugar)
  • Confluence target mode
  • Timeline / "what changed since last sprint" diff
  • Agent-facing query API over the manifest
Honest calibrationv1 guarantees the reference artifact's design polish, structure, and interlinking. Its editorial narrative (verdict, "what this means", worked examples) is the deferred model-enrichment tier — not v1.
