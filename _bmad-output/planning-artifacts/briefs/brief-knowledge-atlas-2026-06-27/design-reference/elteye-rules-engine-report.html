The Rules Engine, and how deeply it is wired into the system

A state-of-the-embedding report: what the requirements promised, what the architecture designed, what the code actually does today — and the distance between that and a flexible spatial-rule platform where you define a rule once and instantiate it against concrete sites and live tracks.

Prepared by Mary · Business Analyst Scope Epics 11 & 12, FR51–FR74, FR82 Basis PRD · architecture.md · live source

The headline

You have a working event engine — but not a spatial rule platform

The rules engine is real, deployed, and generic — it consumes any message stream and fires alerts when scalar field conditions match (speed > 500, severity == 1). But every rule you described — Track-in-Polygon, Line-Crossing, Convoy — needs geometry, state, and entity-binding the engine does not have. "Areas of Interest" exist only as a bounding-box ingestion filter; they are never evaluated inside a rule. And there is no notion of a reusable rule template you instantiate against a concrete site.

In short: the plumbing, persistence, messaging, alert lifecycle and UI are mature. The rule language is the gap. Your vision is mostly greenfield — but it lands on a strong foundation.

Implemented & running Partial / designed-not-built Missing — needed for your vision

01 — Structure

Where the rules engine sits in the system

EltEye is a .NET microservice mesh behind a RabbitMQ backbone. Tracks flow in from external feeds, fan out across services, and the rules-engine is just one more consumer on the bus — which is exactly what makes it generic. Below, each lane is a tier; the highlighted node is the engine and its direct collaborators.

How to read it The engine subscribes to any queue named in a rule (a RuleConsumerManager spins up one consumer per active queue). That is the system's real strength: the same engine that watches tracks also powers EIRMS incident/resource notifications (FR82). It is a generic event → condition → action machine, not a track-specific one.

02 — Runtime

How a track becomes an alert, step by step

This is the path that exists and works today. The order is load-bearing — note where evaluation happens (step 4) and where your spatial vision would have to plug in.

  1. 1
    Feed arrives adsb / ais-gateway

    A gateway polls OpenSky / streams aisstream, maps the response into a Track protobuf, and publishes it to the track.data topic exchange. If an AOI is active, the gateway has already restricted the query to that bounding box (FR61).

  2. 2
    Fan-out on the bus RabbitMQ

    Three competing consumers pick the message up: track-manager persists it, websocket-gateway pushes it live to browsers, and rules-engine evaluates it — but only if a rule targets that queue.

  3. 3
    Payload flattened MicrosoftRulesEngineAdapter

    The engine deserializes the message into a flat { field → value } dictionary. It is deliberately message-type-agnostic: no proto-specific code, so new message types need no engine change.

  4. 4
    Conditions evaluated where your vision must live

    Each active rule becomes a lambda like msg["speed"] > 500 AND msg["source_type"] == "adsb". Only scalar comparisons (> < == != >= <=) on a single message. No geometry, no memory of other tracks, no clock window beyond a fragile in-memory buffer. This is the exact ceiling your three rules exceed.

  5. 5
    Alert persisted, then published rules-engine → rules.events

    On a match, an Alert row is written to PostgreSQL first (rule reference + a JSON snapshot of the triggering values + status New), then an AlertEvent is published. Persist-before-publish prevents ghost alerts.

  6. 6
    Operator sees and works it websocket-gateway → AlertsPanel

    The gateway tags the frame and pushes it over WSS; the browser badge increments and the alert appears in the panel, where it can be Acknowledged or Resolved. Target: under one second end-to-end (NFR-RE1).

03 — The rule today

What a rule actually is in the code

A rule is a single flat record. Crucially, there is no separation between a rule's type and a rule's instance — a rule already carries concrete values baked in, and it binds to a data stream by queue name, never to a concrete entity like "Haifa Port."

// rules table — the entire rule model
{
  "name": "High-speed contact",
  "target_proto_type": "elteye.icd.Track",
  "queue_name": "track.ais",        // ← binds to a STREAM, not an entity
  "rule_category": "statistical",    // statistical | temporal | relational
  "evaluation_criteria": {
    "conditions": [
      { "field":"speed", "operator":">", "value":30 }   // ← scalar only
    ],
    "logical_operator": "AND",
    "window_seconds": null            // temporal = in-memory buffer (lossy)
  },
  "status": "active"
}
What this model can express

Scalar thresholds on one message

  • "Any aircraft faster than 500 kts" — speed > 500
  • "AIS contact of ship-type tanker" — ship_type == "tanker"
  • "Critical incident opened" — severity <= 2 (powers EIRMS notifications)
  • Combine a few with AND / OR
What it cannot express
  • Geometry — "is this lat/lon inside a polygon?" There is no spatial operator and field names must be flat scalars.
  • Relationship to an entity — a rule cannot reference "Site X" or its shape.
  • Cross-track state — "are 3 tracks moving together?" needs memory the engine lacks.
  • Reliable time windows — the buffer is per-replica and lost on restart.

05 — Your three rules

Mapping your vision onto what exists

You gave three exemplars. Each needs a capability the current engine lacks. Here is exactly what each one requires and what is missing.

① Track-in-Polygon — "alert when a track enters Site X"

Needs a point-in-polygon test evaluated inside the rule, against a polygon attached to a concrete site, and entry/exit state (so you alert on the crossing, not every position report while inside).

  • have  Live track positions on the bus; an AOI store with shapes; PostGIS is already a dependency (incidents use geometry(Point,4326)).
  • need  A spatial operator (within / contains); AOI shapes upgraded from bounding boxes to true polygons; enter/leave state per (track, zone); a rule that references a site rather than a queue.

② Line-Crossing — "alert when a track crosses a tripwire"

Needs segment-intersection between two consecutive positions and a line — inherently stateful, because a single position can never cross anything; you need the previous fix too.

  • have  Sequential position stream per track id; geometry libraries available in the .NET/PostGIS stack.
  • need  Per-track "last known position" memory; a line/tripwire geometry type; a crossing predicate; optional direction-of-crossing.

③ Convoy — "alert on a group of tracks moving together"

The hardest: multi-entity correlation over time — proximity + common heading + common speed across several tracks, sustained over a window. This is full Complex Event Processing.

  • have  All tracks on one stream with heading/speed/position fields.
  • need  A stateful CEP engine holding many tracks at once; spatial clustering; a durable time window. This is precisely what the deferred Kinetica/Drools adapters were meant to provide.

07 — The shape of the solution

The abstraction your vision actually needs

What you described — define a generic rule, choose which properties take part, build it as a logical/functional expression, then instantiate and attach it to concrete entities and streams — is a three-layer model the current single-table design collapses into one. Making it real means introducing the missing layers:

The expression model, as you've now specified it

You confirmed two things that escalate the design from a configurator to a real language: predicates return values that flow into other predicates (functional piping), and rules relate pairs and sets of entities (relational joins) — binding a track to fixed geometry or to other live tracks. Concretely, that means a typed functional expression language over the system's entities, plus a complex-event-processing runtime to hold state for the relational cases.

The type system Operands are typed — Entity (Track · Site · Line), Geometry (Point · Polygon · LineString), Scalar, Boolean, and Set<Entity> (the live population, for CEP). Functions carry typed signatures and nest: WITHIN(Point,Polygon)→Bool, CROSSES(Segment,LineString)→Bool, site_of(Track)→Site, distance(Point,Point)→Scalar, plus comparison, boolean, and windowed aggregates (COUNT, AVG).

Your own three exemplars, written in that language — note how each needs a different binding mode and a different amount of state:

// ① Track-in-Polygon — Track × Site, stateless predicate
in_site(T, S)  := WITHIN(T.position, S.polygon)
              // instantiate: S = "Haifa Port"; alert on transition false→true

// ② Line-Crossing — Track × Line, needs per-track memory
crossed(T, L)  := CROSSES( seg(T.prev_pos, T.position), L.geometry )

// ③ Convoy — Track × Track set, full CEP over a window
convoy(G)     := COUNT(G) >= 3
              AND FORALL (a,b) in G:
                    distance(a.pos, b.pos) < 500m
                    AND |a.heading - b.heading| < 10°
                    AND |a.speed - b.speed| < 2kn
              SUSTAINED over 120s

// and your k(A,B): f(g(B)) is now well-typed — g→Site, f(Site)→Bool, composed
k(A, B)       := f( g(B) )    where g(B) := site_of(B),  f(s) := s.threat == HIGH

The current flat condition list is the degenerate case of this language: a single entity, no value-returning functions, boolean-only, no binding. Everything you asked for is a strict superset built from the same parts — which is the good news. Below is how the rule storage reshapes to carry it:

Layer 1 — Rule Template (the generic definition)

e.g. "Track-in-Polygon"

Declares the rule's kind, the predicate it evaluates (point-in-polygon), the entity properties it reads (track lat/lon), and the parameters it needs filled in (a polygon, optional dwell time). Authored once, reused many times.

▼ instantiate
Layer 2 — Rule Instance (the concrete binding)

e.g. "Intruder at Haifa Port"

Fills the template's parameters with concrete values — this polygon (Haifa Port's shape), this stream (track.ais), this severity. Many instances of one template can run at once, each on a different site.

▼ attach
Layer 3 — Bindings (entities & data streams)

Concrete geometry + live feeds

The site polygon (an upgraded AOI), the track stream, and the alert routing. This is where AOIs finally become rule inputs instead of mere ingestion filters — closing the loop your system was clearly built to eventually close.

The pragmatic path — and an honest scope flag The functional-language + relational-CEP model is the single largest item in the whole vision — it adds three net-new sub-components: an expression parser/validator (the language + its type registry of functions), a stateful CEP runtime (per-track memory for line-crossing, the live population for convoy, durable windows), and a spatial layer (true polygons/lines + geometry operators). The good news is the seam already exists: the IRuleEvaluator adapter pattern is the home for it, and the deferred Kinetica/Drools adapters (stories 12.6/12.7) were chosen for exactly this native temporal + complex-event capability — the flat in-house Microsoft engine cannot reach convoy on its own. Build the language and a CEP-backed evaluator behind that interface, add the template/instance schema on top of today's rules table, and the bus, persistence, alert lifecycle and UI all stay as-is. Not a rewrite — a new evaluator and a new front-door grammar.

08 — Distributed evaluation

Splitting one rule across specialized engines

You want a rule's work decomposed by predicate kind and farmed to the engine best suited to it — the spatial part to a dedicated geospatial service, the scalar/temporal part to the regular engine, optionally a commercial accelerator for high-volume streams — then the partials recombined. Because the rule is already a typed expression tree, this is a clean scatter-gather:

Rule Coordinator / planner

Compiles the expression tree into an execution plan and dispatches each node to the evaluator that fits its type. Reads & writes shared state in Redis.

Your worked example, split

"A rule checks a track's geography and its type and speed" decomposes as:

// rule:  WITHIN(track.pos, SITE)  AND  track.type == X  AND  track.speed > Y
geospatial service  →  { tracks inside SITE }              // gRPC, OSS geo backend
regular evaluator   →  { tracks where type==X AND speed>Y } // in-process / RMQ
combine (AND)       →  INTERSECT by track_id within the same tick  // the "union" step, keyed
                    →  alert on the surviving set
On the word "union" The recombination operator is dictated by the expression tree, not fixed. For your AND-rule it is an intersection of the two engines' matching track-sets; a true union only applies to OR nodes. Either way the partials must be correlated by entity-id within the same time window so both engines reference the same track at the same instant — otherwise an AND-rule over-fires.

09 — Geo-service contract

The gRPC API the spatial work hides behind

This is the seam everything swaps behind, so it is worth pinning first. The design keeps the service stateless (pure functions of position + reference geometry) and pushes all memory — previous position, geofence membership, convoy windows — into Redis. The contract speaks spatial intent (contain / cross / cluster), never backend SQL, so an OSS implementation and a commercial one satisfy the same proto.

service GeospatialEvaluator {
  // unary — single predicate node, cheapest for on-demand dispatch
  rpc TestContainment        (ContainmentRequest)        returns (ContainmentResponse);
  rpc TestLineCrossing       (LineCrossingRequest)        returns (LineCrossingResponse);
  // unary batch — one Coordinator tick over a track-set, atomic to JOIN
  rpc EvaluateContainmentBatch (BatchContainmentRequest)  returns (BatchContainmentResponse);
  rpc EvaluateProximityCluster (ProximityClusterRequest)  returns (ProximityClusterResponse);
  // server-streaming — long-lived geofence push (ENTER / EXIT / CROSS)
  rpc SubscribeGeofence      (GeofenceSubscribeRequest)   returns (stream GeofenceEvent);
  // bidi — realtime ingest: samples in, transition events out
  rpc EvaluateStream         (stream TrackSample)         returns (stream GeofenceEvent);
}

// THE JOIN KEY — stamped on every result so the Coordinator can recombine
message EvalKey {
  string entity_id = 1;   Timestamp tick = 2;   // Coordinator-assigned cycle
  string rule_id   = 3;   string predicate_id = 4;
}
How the combine actually works The Coordinator stamps one tick into every sub-request — to this service and to the scalar evaluator. Both return matches keyed by (entity_id, tick), so recombination is pure set algebra correlated by that key: AND → intersect, OR → union, NOT → complement against the candidate population. predicate_id lets one tick carry several spatial nodes from the same tree. This is the precise form of the "union" you described.

Rule of thumb from the design: the service answers "is it true now"; Redis + Coordinator answer "did it change" and "has it held."

Open questions for a human (1) Does the ENTER/EXIT edge live in the service or the Coordinator? (2) What time-quantisation aligns streamed spatial events with polled scalar verdicts in the JOIN? (3) Is convoy "sustained over T" the Coordinator's job or a windowed RPC? (4) Geometry-cache invalidation — push or version-check? (5) Are any predicates genuinely 3D (altitude bands), or 2D-on-ground?

Recommended OSS default

  • Tile38 (optional but recommended) — battle-tested enter/exit/cross + roaming fences that map almost 1:1 onto convoy, instead of hand-rolling the state machine.

When to swap in commercial
  • Sustained ingest outgrows a single node (Tile38 fences drop to ~6k SET/s with ~23k fences).
  • Fence × track cross-product explodes (thousands of fences × thousands of tracks/tick).
  • Correlated temporal CEP at scale ("formation held for M min").
  • Single-writer HA becomes the bottleneck.
Top risks the research flagged (1) Tile38 throughput cliff with many active fences + single-writer — capacity-test with realistic fence counts. (2) With NTS you own the enter/exit state machine, dedup, and out-of-order/replay correctness. (3) SingleStore geo limits (no MULTIPOLYGON in columnstore; APPROX_* has false positives). (4) Kinetica needs NVIDIA GPUs — which lindev3 does not currently have — and neither commercial option has a first-class .NET SDK, so design the gRPC façade around eventual events + idempotency now or the swap leaks.

11 — The Site entity

The missing first-class entity your rules bind to

Spatial predicates need something concrete to point at — and today there isn't one. AOIs are bounding-box ingestion filters, too thin to be a rule target. The model needs a new first-class entity: the Site — a named place with real geometry and classification, the "S" in WITHIN(track, S).

The Site entity

id · name · geography · classifications

  • id — stable UUID, referenced by rule instances & the geo-service
  • name — human label ("TelAviv", "Haifa Port")
  • geography — true Polygon / MultiPolygon (PostGIS, WGS84) — not a bounding box
  • classifications — taxonomy/tags (port · airfield · city · restricted-zone) that become rule inputs themselves
site-manager service

Its own home, mirroring the house pattern

  • A dedicated site-manager service — like aoi-manager, but richer
  • Dedicated PostgreSQL sites schema with real PostGIS geometry
  • REST CRUD for operators (C2B) + MCP for the AI chat
  • Resolved by the geo-service / coordinator via GeometryRef (load once, cache)
Site vs. AOI They stay distinct: AOIs remain the ingestion bounding-box filter (what data enters the pipeline); Sites are the named reference geometries that rule instances bind to and that spatial predicates evaluate against. A Site's classifications open a further door — "alert in any restricted-zone Site" — without naming each one.

12 — Conversational authoring

Speak a rule, and the system builds it

The point of a typed language plus a Site entity is that an operator can author in plain words. "Alert if more than one Train in Tel-Aviv is going faster than 40 km/h" must become a complete, activated rule — combining a site, a track type, a speed threshold, and a count — bound to a concrete Site.

intent:  "more than one Train in Tel-Aviv faster than 40 km/h"

parse →   site   = resolve / create Site "TelAviv"      // polygon
          type   = track.type == "Train"             // ground-traffic / GTFS, Epic 21
          speed  = track.speed > 40 km/h
          count  = COUNT(...) > 1

DSL  →    alert when
            COUNT( T in tracks :
                   WITHIN(T.pos, Site("TelAviv"))
                   AND T.type == "Train"
                   AND T.speed > 40kmh ) > 1

act  →    1 create template   CountInSiteByType(site, type, speed, n)
          2 instantiate        bind site=TelAviv, type=Train, speed=40, n=1
          3 activate           on the ground-traffic stream
          4 alert              "2 trains in TelAviv exceeding 40 km/h"
Why the typed language is what makes this work Natural-language authoring rides the existing llm-backend + mcp-aggregator. The typed DSL is precisely what makes intent tractable: the LLM maps words onto typed functions, and the engine type-checks and dry-runs before activating — so a malformed rule is caught, not fired. New MCP tools sit atop today's rules.create/activate: sites.resolve/create and rules.author_from_intent (compose template + instance). Operator-in-the-loop: preview and confirm before it goes live.

14 — Next moves

Where the treasure is buried

If you want to move from this report toward building it, these are the decision points I'd put in front of you next — each is a fork worth deciding deliberately before any code:

  • The gRPC geo-service contract — define the stable API first (within / crosses / near + enter-exit events). It is the seam everything else swaps behind, so it is the highest-leverage thing to pin down.
  • OSS geo backend — confirm the default: NetTopologySuite + PostGIS for stored/ad-hoc spatial, and/or Tile38 for streaming geofence events. Kinetica / SingleStore stay as commercial swap-ins.
  • Redis state model — design the shared keys (per-track last-position, window buffers, live population) that retire the in-memory buffer and unlock horizontal scale-out.
  • Expression language + planner — the parser/validator/type-registry, and the coordinator that splits the tree and combines partials by the boolean operators.
  • Template/instance schema — the two missing layers over today's flat rules table.
  • Authoring UX — there is no rule-building UI at all today; a builder (pick template → pick entity/zone → set parameters) is net-new frontend work.
My recommendation as analyst Start with Track-in-Polygon — but build it through the full distributed path, not a shortcut. It is the smallest end-to-end proof of every load-bearing decision at once: the gRPC geo-service contract, the OSS backend, Redis-held enter/exit state, the coordinator's split-and-combine, and the template→instance→binding model (it turns AOIs from filters into predicates). Get that one rule flowing scatter-gather and the pattern for line-crossing and convoy is the same shape at higher state. Happy to facilitate a brainstorming or requirements session to spec the geo-service API — that is exactly the next hunt.
