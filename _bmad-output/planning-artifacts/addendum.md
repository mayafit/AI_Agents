# PRD Addendum — F26 (Global Install & Federated Knowledge Stores)

Depth that earned a place but does not belong in the PRD itself: rejected alternatives,
mechanism-level decisions, and technical-how that architecture (P5-9) should inherit rather than
rediscover.

Companion to `prd.md` (index) and the two F26 capability shards. Audit trail lives in
`.memlog.md`, not here.

## Rejected alternative — `.ma-agents.json` as the binding file

**Proposed first, then rejected.** The initial recommendation was to extend the project-root
`.ma-agents.json` with the knowledge-store bindings, on the grounds that it sits at the project
root, is not gitignored, and was already established as a single source of truth by Story 27.12.

**Why it lost.** `_bmad-output/project-layout.yaml` already exists and is a better fit on every
axis that mattered:

| Axis | `.ma-agents.json` | `project-layout.yaml` |
|---|---|---|
| Purpose | Skills manifest / install state (`lib/installer.js:10`) | Cross-repo knowledge-location record (FR122) |
| Already specified? | No — would need new semantics | Yes, FR122, Story 16.2 |
| Already implemented? | For skills only | Yes, `bin/cli.js:605-672`, called "the authoritative source" at `cli.js:672` |
| Committed? | Yes, not gitignored | Yes — `_bmad-output/` is deliberately tracked per FR58 |
| Conceptual fit | Would mix install state with project topology | Purpose-built for exactly this |

Loading knowledge topology into the skills manifest would have conflated two unrelated
lifecycles: install state changes when you install, project topology changes when the project
reorganises. Keeping them separate means `ma-agents bind` (FR252) can rewrite topology without
touching install state.

**Consequence for F26.** The requirement became "make the existing file authoritative and
unconditional" (FR263) rather than "invent a new binding file" — a smaller change with an
existing implementation to extend.

## Mechanism — generating `config.yaml` from `project-layout.yaml`

FR264 states the contract (config.yaml becomes generated); this is the how, for P5-9.

The reason this indirection exists rather than pointing skills at the committed file: **39
existing references**. Seven skills read `{project-root}/_bmad/bmm/config.yaml` explicitly and 32
use `{output_folder}` derived from it. Repointing all of them would touch every skill and every
mil498 prompt, with a large regression surface and no user-visible benefit.

Generation direction is one-way, committed → per-machine:

```
_bmad-output/project-layout.yaml   (committed, authoritative, team-shared)
        │  generated by install and by `ma-agents bind`
        ▼
_bmad/bmm/config.yaml              (gitignored, per-machine, what skills read)
```

Open mechanism questions for P5-9:

- When does generation fire? Install and bind are obvious. Should a skill regenerate on activation
  if `project-layout.yaml` is newer than `config.yaml`, or is staleness a reported error?
- What happens to a hand-edited `config.yaml`? Overwrite, warn, or merge. Note the existing
  file header already declares itself installer-managed and overwritable, which argues for
  overwrite-with-notice.
- Does `config.user.yaml` (personal overrides) survive generation? It must — it is the documented
  place for per-developer pins.

## Mechanism — MCP-conditional Confluence routing

FR261 requires following `mcp-detection-pattern-spec.md` rather than a new mechanism. Worth
recording why that spec is the right reuse:

It was written for Story 17.22 / Decision P2-11 as the canonical backend-routing pattern for the
13 sprint-management skills choosing between Jira and the file system. It explicitly covers
detection, routing, and failure handling, and explicitly does *not* create executable code or
require credential management — each consuming skill embeds the template itself. That is exactly
the shape the Confluence backend needs, and it means a reviewer already familiar with the Jira
path can read the Confluence path without learning a second convention.

The `knowledge_backend` field name in `epics.md` Story 14.2's deferral note is the field F26
realises as the per-store `backend` value (FR257). Story 14.2 should be reframed against FR254–
FR266 rather than implemented as originally scoped.

## Sizing note — why the two-store cut is where it is

The cut follows the systems-engineering distinction the user framed it in: *system requirements*
(what the system must do) versus *software requirements* (how it is built). It aligns with how
the artifacts are already produced and reviewed — brief and PRD by product, architecture/UX/epics
by engineering — which is also why the two often want different homes and different visibility.

The cut does not align with BMAD's existing `planning_artifacts` / `implementation_artifacts`
split, which is phase-based rather than concern-based. That mismatch is the root of Open Item #1
(where story files belong) and is the thing to resolve before epic creation.
