## Findings

### Critical

- **[Critical] The spec says setup answers go to the wrong file. v7 setup writes team answers to `_bmad/config.toml`, and the set contradicts itself on this.** PRD-F29:210 says "Answers are stored by `bmad setup`: team-scoped keys in `_bmad/custom/config.toml`". FR293 (PRD-F29:310) says the answers are "committed with the project in `_bmad/custom/config.toml`". The ma-atlassian migration writes "team keys to `config.toml`" (PRD-F29:280) and, in ADR:258, "to `_bmad/custom/config.toml` (team keys)". Story 36.1 AC5 (`36-1-…md:31`) expects to find answers in "`_bmad/custom/config.toml` vs `config.user.toml`". The pinned v7 behaves differently. `setup.py` has `TEAM_CONFIG = "_bmad/config.toml"` (`setup.py:35`) and writes team answers there (`:296`). `docs/customize/customize-bmad.md:280-281` says `_bmad/config.toml` is "setup-owned … setup answers" and `_bmad/custom/config.toml` is "human-authored … team overrides". `find_pending_questions` (`setup.py:2121`) treats a team question as answered only when the key is in `_bmad/config.toml`. So a migration that writes team keys to `_bmad/custom/config.toml` leaves every ma-atlassian question pending, and the next `bmad setup` or installer run asks them again. ADR:167 and STRUCT:219 describe the v7 layering correctly, so the set disagrees with itself. **Fix:** make PRD-F29:210 read "Answers are written by `bmad setup`: team-scoped keys to `_bmad/config.toml` (setup-owned, committed), user-scoped keys to `_bmad/custom/config.user.toml`. A team may override a key in `_bmad/custom/config.toml`." Make FR293 read "…setup answers in `_bmad/config.toml`, read through `resolve_config.py`…". Both migrations must write module answers through `setup.py --module-answers`, not into files directly. Change 36.1 AC5 to expect `_bmad/config.toml`.

- **[Critical] The answers-file contract does not match `setup.py --module-answers`, so `update`, any re-install and the "same answers file" guarantee fail.** PRD-F29:142-145 says "`--answers` takes a TOML file with one table per module code (`[ma-atlassian]`, `[ma-knowledge]`, …)". Install step 5 (PRD-F29:157) says "Write the answers file". `update` (PRD-F29:118) "re-runs the install sequence". FR298 (PRD-F29:318) says "the wizard and the `--yes` path run the same code with the same answers file". At the pin, `load_module_answers` accepts only a top-level `modules` table: it raises "must contain only module answer tables" when `set(data) != {"modules"}` (`setup.py:2149-2150`). The documented shape is `[modules."<code>"]` (`references/setup.md`, Config step). `validate_module_answers` also rejects any answer that is not a *pending* question ("contains modules.x.y, which is not a pending question", `setup.py:2202-2205`) and any pending question left unanswered (`:2206-2219`). The first install therefore works only with the right table shape. Every later `update` or `install` that sends the full answers file fails, because the questions are no longer pending. Story 36.1 AC5 (`36-1-…md:31`) already states the consequence, "the installer must list questions first and send only pending ones", but no requirement says so. **Fix:** in PRD-F29 Install sequence and FR284: "5. Run `setup.py --list-config-questions` (with one `--root` per active skills folder). Answer each pending question from `--answers`, from the wizard or from its declared default, and write only those answers to a temporary file as `[modules."<code>"]` tables with quoted keys. 6. Run `setup.py --module-answers <file>`, then delete the file." State that `--answers` is the installer's own input format and that the installer translates it. Apply the same wording to ADR:264 and PATTERNS:246.

- **[Critical] Marker-delimited blocks inside one TOML file cannot do what the spec promises.** PRD-F29:248-250 and ADR:207 say bind writes "a block between `# ma-atlassian:start` and `# ma-atlassian:end` in `_bmad/custom/<skill>.toml`". PRD-F29:256-258, FR289 (PRD-F29:306) and ADR:209 say "Keys set outside the markers win". TOML forbids a duplicate key and a re-opened table. `read_store.py` loads the project file with one `tomllib.loads` (`read_store.py:37`, `:48`), and the customization resolver parses each layer as one document. A user key with the same name as a key inside the block is therefore a parse error, not an override. A block that opens `[workflow]` or `[agent]` in a file where the user already has that table makes the whole file invalid, and the skill then fails to activate. Collisions are defined per key (FR291), not per table, so this case falls through. `bmad-agent-po` needs `[agent] persistent_facts` and `[workflow] board_after`, `store_after` in one file, which makes it likely. **Fix:** replace the block model in FR289, FR291, ADR:207-209 and PATTERNS:232 with key-level ownership. "Bind parses the file, inserts each owned key into its existing table (creating the table header only when absent), and brackets each owned key line with `# ma-atlassian:start <table>.<key>` / `# ma-atlassian:end` comment lines. A key the user already set is a collision: bind leaves the file unchanged and reports it. For `ticketing-store-config.toml`, bind writes only keys the file does not yet define." Delete "keys set outside the markers win". Add a 36.4 AC6 case for a user file that already has `[workflow]`.

### High

- **[High] Migrations and `bmad status` are LLM-driven skill flows, but the spec has a Node CLI and CI run them as if they were commands.** `update` "then `bmad migrate` for any module whose version changed" (PRD-F29:118). `status` prints "the output of `bmad status`" (FR302, PRD-F29:321; ADR:192). NFR84 requires "`bmad status` reports it current" (PRD-F29:327). NFR87 "CI upgrades a … fixture … and asserts that no artefact is lost" (PRD-F29:329). FR294 makes every migration "idempotent … never overwrites" (PRD-F29:316). At the pin, `references/migrate.md` step 3 says "Read the chosen file whole and do what `guide` says". A migration is a prose file an agent follows after user approval of a plan. Story 36.1 AC9 (`36-1-…md:35`) confirms it is "LLM-driven … no dry-run mode exists". No CLI entry point exists for `bmad migrate` or `bmad status`. The script equivalent of status is `setup.py --status`. A Node installer cannot run a migration, and CI cannot assert deterministic idempotence of an agent following prose. Ordering is not guaranteed either. `migrate.md` runs migrations in `knowledge.py` listing order, so "runs after `bmad migrate method`" (PRD-F29:61, ADR:240) holds only if `detect` encodes it, and the spec defines no `detect`. **Fix:** (1) `update` and the upgrade end by printing "ask `bmad` to run `bmad migrate`" with the module list; the installer never runs a migration. (2) `status` and NFR84 use `uv run --no-cache <bmad>/scripts/setup.py --project-root . --skill <bmad> --status` and its `current` field. (3) Move the deterministic part of each migration into a script declared in a member skill's `[skill] scripts` (for example `ma-ops-dev-epic/scripts/migrate_v6_backlog.py` and `ma-atlassian-bind/scripts/migrate_binding.js`). The `migration-<n>.toml` `guide` calls that script. FR294 idempotence and NFR87 are then asserted on the scripts in CI. (4) Specify each migration's `detect`. For ma-ops: "`archive-v6/sprint-status.yaml` exists under an initiative and contains a `backlog:` or `sprints:` key".

- **[High] A `file:` update source cannot be fixed at `bundle build` time, and the installer is forbidden to fix it at install time.** ADR:190: "`bundle build` sets them to a `file:` source pointing at the bundled snapshot". STRUCT:203 says "file: update source". FR297 (PRD-F29:317): "Bundled modules record `update_source` as `file:`". The bundle is built on a maintainer machine and later lives inside an npm install directory whose path is not known at build time. It also changes when the package is upgraded. A relative `file:` resolves against the *project root* (`setup.py:1919-1923`), not against the bundle. ADR:270 and PATTERNS:255 forbid the installer to edit skill content, so it cannot rewrite the path either. The same section (ADR:190) gives the repository value as `github:<org>/ma-bmad-extensions/skills` with `<org>` unresolved, and FR297 says "a Git-hosted install records `https://`". Story 36.1 premise (3) (`36-1-…md:21`) and `module-files.md:65` show that the channel is baked into the published files. An install from an intra-perimeter Git host therefore records whatever the tag's files say, which is not `https://`. **Fix:** state the concrete value: "`update_source` and every member `source` are `github:<concrete-org>/ma-bmad-extensions/skills`." Then choose and state one offline rule. Either (a) the installer copies the bundle's module trees to `<scope>/.ma-agents/modules/` and `bundle build` writes `file:.ma-agents/modules/<repo>` (project scope, relative to the project root as `setup.py` resolves it), or (b) offline installs keep `github:` and accept `could-not-check` in `setup.py --status`. Delete "a Git-hosted install records `https://`" unless the mirror publishes rewritten files, and if it does, say who rewrites them.

- **[High] `uv.toml` cannot carry the `UV_PYTHON` setting, its location is unspecified, and a project-root `uv.toml` takes over the user's own Python project.** FR282 (PRD-F29:292), PRD-F29:150-153, ADR:223 and PATTERNS:245 say the installer writes "the same settings to a `uv.toml` in the install scope". uv's settings file has `find-links`, `offline`, `no-cache`, `python-preference`, `python-downloads` and `python-install-dir`, but no key equivalent to `UV_PYTHON`/`--python`. "The install scope" is not a path uv reads. uv discovers `uv.toml` in the working directory and its parents, plus the user-level config directory (`~/.config/uv/` or `%APPDATA%\uv\`), never `~/.ma-agents/`. A `uv.toml` at the project root also takes precedence over the user's `pyproject.toml` `[tool.uv]` and forces `offline` on their own project. Story 36.2 AC3/AC4 (`36-2-…md:27-28`) actually installs the interpreter with `uv python install` into `UV_PYTHON_INSTALL_DIR` and adds `UV_PYTHON_DOWNLOADS=never`. Neither appears in F29. **Fix:** name the file and keys. "Project scope: `<project-root>/.ma-agents/uv.toml`, selected for skill activations by `UV_CONFIG_FILE` set in the injected `ma-agents` block's environment guidance. Global scope: the uv user config file. Keys: `python-install-dir = <runtime>/python`, `python-preference = "only-managed"`, `python-downloads = "never"`, `find-links = [<runtime>/wheelhouse/<platform>]`, `offline = true`, `no-cache = true`." Replace `UV_PYTHON` in the env list with `UV_PYTHON_INSTALL_DIR` + `UV_PYTHON_PREFERENCE=only-managed` + `UV_PYTHON_DOWNLOADS=never`. Add a risk line about an existing user `uv.toml`.

- **[High] Running `npx skills@<bundled>` contradicts "attempting no network access".** Install step 3 (PRD-F29:155) and ADR:264 say `npx skills@<bundled> add …`. FR283 (PRD-F29:293) says "runs it from the bundle … attempting no network access". `npx <pkg>@<ver>` resolves the spec against the npm registry unless that exact version is already in the npm cache, which is never true on a fresh air-gapped host. Story 36.1 AC2 (`36-1-…md:28`) tests a different thing: "the `skills` package pre-installed from a packed tarball". **Fix:** "The installer unpacks `bundle/skills-cli/skills-<skillsCli>.tgz` into `<scope>/.ma-agents/skills-cli/` and runs `node <that>/<bin entry> add <bundle path> --skill … -y --agent <tool>` with the telemetry opt-out environment variables 36.1 AC2 records." Apply the same in ADR:264 and STRUCT:225.

- **[High] Under the F29 version scheme, the 4.x pre-release that Story 36.6 cuts is a 3.x installer.** 36.6 AC8 (`36-6-…md:30`): "this pre-release's `ma-agents install` command is still the 3.x install path (it installs bmad-method 6.10.0)". F29's product lines table (PRD-F29:28) defines 4.x as "thin offline installer (npm `ma-agents` 4.x) + `ma-bmad-extensions` modules on BMAD v7 | pre-release (dist-tag `next`)". FR298 says the 4.x package provides `install`, `update`, `status`, `uninstall`, `bundle build`. Epic 39's goal (EPICS:5949) adds "It ships on the BMAD v7 GA tag only", which contradicts FR281's `next` pre-releases of 4.x. So `4.0.0-next.0` is a package that does not implement the 4.x installer. Epic 39 forbids 4.x installer pre-releases, and FR281 requires them. **Fix:** pick one. Either (a) 36.6 publishes nothing to npm, its output is the CI evidence and a git tag `v4-gate-<sha>`, and the first `4.0.0-next.N` is cut at the end of Epic 39 before 39.5. Or (b) delete "It ships on the BMAD v7 GA tag only" from Epic 39 and state that `4.0.0-next.N` packages carry the 4.x installer from 39.2 onward. Under either option, remove the "still the 3.x install path" sentence.

- **[High] Epic 36, its stories and the sprint tracker trace to 3.x requirements that F27 marks "not implemented", and to v6 mechanisms.** Epic 36 FR Coverage (EPICS:5861) lists "FR277, FR278, FR279 … NFR74". Stories 36.2/36.3/36.4/36.5/36.6 cite FR277/FR278/FR279 (`36-2-…md:7`, `36-3-…md:7`, `36-4-…md:7`, `36-5-…md:7`, `36-6-…md:7`). `sprint-status.yaml:518-525` gives "FR277–FR284" and "FR277, FR278". `bmad-platform-currency.md:26` says "Not implemented by this package: FR275–FR279". FR278 is "validated against the v6.12 contract". NFR74 says the opposite of what 36.2 claims for it. 36.2 says "NFR74 (skill scripts run through `uv run`; the installer's own CLI is Node)". NFR74's text is "A uv-missing install must still succeed … under v6.10.0 … control-plane Python stays on the `python` interpreter (not `uv run`)". Epic 37 (EPICS:5896) claims "FR104–FR106 are satisfied per module". Those are the v6 `module.yaml`, `config.yaml`/`module-help.csv` setup skill and agent-folder requirements, which v7 replaces with `bmod.toml`, `help/help.md` and `roster.toml`. The 36.4 contract validator, the uv runner guard and the instruction-file test have no F29 requirement of their own. **Fix:** add F29 FRs for the gaps: "FR303 Contract validator: every owned `customize.toml` and every bind output resolves through the pinned `resolve_customization.py`, and every bound slot is defined at `bmadRef.core`." "FR304 uv execution: the installer spawns uv only through one runner module with `run --no-cache`." Re-point the traces: FR277→FR282/FR304, FR278→FR303, FR279→FR298 (`engines.node`). Drop NFR74, and drop FR104–FR106 from Epic 37. Make the same edits in `sprint-status.yaml`.

- **[High] The config-question defaults are impossible in v7 and unsafe under `--yes`.** PRD-F29:215-223 gives `jira_site`, `jira_project_key`, `confluence_site` and `planning_space` the default "—" and `tickets_space` the default "`planning_space`". PRD-F29:143-145 says "a question with no default and no answer stops the install". In v7, `default` is a mandatory string key of every `[[bmod.config_questions]]` entry (`QUESTION_KEYS = {"key","prompt","default"}`, `setup.py:27`; a missing key raises, `:1638-1641`). A "no default" question cannot exist. The only placeholder expanded in a default is `{directory_name}` (`setup.py:2124`), so a default cannot name another answer. ADR:244-254 sets every default to `""`. Under `--yes`, the installer then accepts an empty Jira site and project key without stopping, and bind writes a store that cannot work. **Fix:** in PRD-F29 and ADR, give every question the default `""` and state "required: a non-empty answer" for `jira_site`, `jira_project_key`, `confluence_site` and `planning_space`. The installer refuses `--yes` without those answers when `ma-atlassian` is selected. `ma-atlassian-bind status` reports "unbound: missing answer <key>". `tickets_space` defaults to `""`, which consumers read as "use `planning_space`". Delete the "no default" sentence at PRD-F29:144-145.

### Medium

- **[Medium] The ma-atlassian migration has three different step orders.** PRD-F29:279-281: "writes the module answers …, runs `ma-atlassian-bind bind`, deletes the old markers". ADR:258: "writes the module answers …, deletes the 3.x marker blocks, runs `ma-atlassian-bind bind`". Story 38.5 (EPICS:5935): "writes the module answers and the new overrides, deletes the old markers". Running bind while the 3.x blocks are still present makes bind see the old keys as user-authored values and report collisions, so only ADR:258's order works. **Fix:** use ADR:258's order everywhere: "answers → delete 3.x blocks → bind → report".

- **[Medium] The IDE-injection integration test covers two writers in one place and three in another.** FR301 (PRD-F29:320) says "an integration test runs all three writers on the same `AGENTS.md` in both orders". ADR:269 says "an integration test runs both in either order and checks both blocks". Epic 36 and Story 36.5 test three owners over six orders. FR301 also says "both orders" for three writers, which is meaningless because three writers have six. The story key `36-5-agents-md-two-writer-test-v7` (`sprint-status.yaml:523`) says two. The upstream marker `bmad:context` (`36-5-…md:94`) is named only in the story. **Fix:** FR301 and ADR:269: "an integration test runs the three writers (`ma-agents`, `ma-standards`, the upstream `bmad-project-context` block) in all six orders, re-runs each, and asserts that each block and the user prose survive byte-identical". Name the upstream markers in ADR as "read from `skills/bmad-project-context/references/template.md` at `bmadRef.core`".

- **[Medium] The upgrade backup has a different scope in each document.** PRD-F29:187-188 and FR294 back up "`_bmad/`, `_bmad-output/` and IDE instruction files". ADR:268 backs up "`_bmad/` and the output folder" with no IDE files. Story 39.3 (EPICS) says "after a backup" and gives no scope. The uninstall step removes the 3.x `MA-AGENTS-START` block from those IDE files (`36-5-…md:96`), so ADR's scope loses user prose if that removal fails. **Fix:** ADR:268: "backs up `_bmad/`, the 3.x output folder (`_bmad-output/` or the configured one), `.ma-agents.json` and every instruction file the 3.x installer wrote (`AGENTS.md`, `CLAUDE.md`, `.clinerules`, `.roomodes`, `.github/copilot-instructions.md`) to `.ma-agents-backup-<datetime>/`". Use the same path in FR294 and 39.3.

- **[Medium] `ma-ops-dev-epic` writing story status only through the plan file bypasses the Jira store that FR289 says owns transitions.** FR292 (PRD-F29:309), ADR:225 and PATTERNS:239: "writes story status only through `bmad-build`'s plan file". FR289: "Jira transitions run through `bmad-agent-po`'s board verbs; no other skill carries Jira routing text". The pinned `docs/plan/set-up-the-ticket-tree.md:182` says build stops at `built`, only the user or an orchestrator marks done, and with a tracker the user tells Sofia to "start"/"mark … done" so that the card moves. An orchestrator that edits the plan file leaves the Jira issue in "In Progress". **Fix:** FR292: "…marks a story `done` and starts a story through `bmad-agent-po` board requests ('start story <id>', 'mark story <id> done'), so the configured store moves its card; it never edits a plan's status line itself."

- **[Medium] Modules depend on `method` skills but declare only `bmad` as required.** PRD-F29:64 and FR302 say `required_skills` names `bmad` core only, and PRD-F29:18 says every module "works on a vanilla BMAD v7 project". Yet several owned skills need method skills. `ma-ops-dev-epic` needs `tickets.py`, which ships with `bmad-agent-po` (`skills/bmad-agent-po/bmod.toml`: `scripts = ["scripts/tickets.py"]`, installed to `_bmad/method/scripts/`), and it also needs `bmad-build`. `ma-knowledge-atlas` reads the initiative store. `auto-bug-detection` reads `tickets.py` (ADR:238). `ma-atlassian` binds `bmad-agent-po`. A module installed onto `core-tools` alone installs cleanly and then fails at run time. **Fix:** "`bmod-ma-ops` and `bmod-ma-atlassian` declare `required_skills = [{ skill = "bmad", … }, { skill = "bmad-agent-po", version = "<method version>", source = "github:bmad-code-org/BMAD-METHOD/skills" }, { skill = "bmad-build", … }]`. `ma-knowledge-atlas` and `auto-bug-detection` check for `_bmad/method/scripts/tickets.py` at activation and report its absence." Narrow PRD-F29:18 to "a BMAD v7 project with the `method` module".

- **[Medium] Uninstall by `skills-lock.json` removes skills the user installed, and the 4.x role of `.ma-agents.json` is undefined.** FR298 and PRD-F29:181: uninstall "removes the skills it installed (per `skills-lock.json`)". `skills-lock.json` is the Skills CLI's lock for every `npx skills add` in the project, including the user's own. In global scope it is not `skills-lock.json` at all, but `$XDG_STATE_HOME/skills/.skill-lock.json` or `~/.agents/.skill-lock.json` (`setup.py:639-645`). PATTERNS:247 says the installer writes `.ma-agents.json`, and STRUCT:214 says the installer "owns `.ma-agents.json`". F29 mentions `.ma-agents.json` only as a 3.x input. **Fix:** "The installer records in `<scope>/.ma-agents/install.json` every skill name, agent target and source it added. `uninstall` removes exactly those entries through the Skills CLI `remove` command. `.ma-agents.json` is read only on a 3.x project." Update PATTERNS:247, STRUCT:197 and STRUCT:214 to match.

- **[Medium] The Jira starter's store-file keys are never named, and the whole-starter copy goes against upstream guidance.** FR289 fills "the site, project key and MCP server name". The upstream starter schema uses `[tickets] store`, `key`, `site`, `access`, `fields`, `reference` and `[verbs]` (`config/jira-ticketing.toml:13-20`). F29 never says which keys hold `jira_site`, `jira_project_key` or `jira_mcp_server`, or how MCP-vs-REST reaches the verbs. `references/store-setup.md` step 2 says to "Copy nothing else from the starter; cut a whole-starter copy down to `store`, the address fields, and the team's changes". For a store with no starter, `read_store.py` uses the project file alone (`read_store.py:51`), which explains the whole copy, but the spec never records that the copy is deliberate. **Fix:** add a table to PRD-F29 "Jira store": "`[tickets] store = "jira-onprem"`, `site = <jira_site>`, `key = <jira_project_key>`, `mcp_server = <jira_mcp_server>` (read by our `access` text and `[verbs]`); `[verbs]` setup, create, transition, query, assign, link: REST forms and MCP forms." Add one sentence: "The whole starter is written because `jira-onprem` has no starter in `bmad-agent-po/config/`."

- **[Medium] The validator's "one block per file" rule contradicts the bind design.** Story 36.4 AC6 (`36-4-…md:41`): "`ma-atlassian` markers are balanced, not nested, and appear at most once per file". ADR:207: bind "writes each override as a block", and `bmad-agent-po` gets three overrides in one file (ADR:204-205), as do `bmad-prd`, `bmad-architecture` and `bmad-facilitate` (two each). **Fix:** align with the key-level model from the third Critical finding. AC6 should read: "each marker pair brackets exactly one owned key; pairs are balanced and not nested; a key appears in at most one pair".

- **[Medium] The offline environment varies between F29 and Story 36.2, and 36.2 tells users to set it by hand.** F29 exports `UV_PYTHON`, `UV_FIND_LINKS`, `UV_OFFLINE=1`, `UV_NO_CACHE=1`. 36.2 AC4 adds `UV_PYTHON_DOWNLOADS=never` and installs into `UV_PYTHON_INSTALL_DIR`. 36.2 AC8 (`36-2-…md:32`) documents "the exact env vars and where to set them (shell profile, IDE agent env)", which contradicts FR282's statement that later activations "find the runtime without the installer" through `uv.toml`. **Fix:** after the `uv.toml` fix above, 36.2 AC8 should say "the `uv.toml` keys the installer writes, and the equivalent env vars for a manual install". ## Verdict

**On narrative: largely yes. On being a v7 specification: not yet.**

The restructuring removed almost all of the process language the 2026-11-07 review flagged. F29, P5-11 and the stories describe the 4.x line in the present tense, with a full package map, a bind target table whose slots match the pinned `customize.toml` files (spot-checked: `bmad-prd:108/127`, `bmad-architecture:75/81`, `bmad-facilitate:24/36`, `bmad-build:17`, `bmad-agent-po:21/91/103` are all correct), concrete ticket-store maps that match upstream's Jira starter, and correct v7 names (`bmod.toml`, `retired.toml`, `roster.toml`, `migration-<n>.toml`, `tickets.py`, `ticketing-store-config.toml`, `--module-answers`, `skills-lock.json`). A sample of story citations into the worktree and the pinned tree was accurate to within a few lines (`setup.py:1060-1066`, `:639-645`, `:2202-2211`; `test/uv-transition-resilience.test.js:194`; `package.json:3`, `:57-58`; `offline-install.yml:68`; `README.md:364`; `lib/installer.js:1332`). Only a few history pointers remain.

The set does not yet read as an implementable specification of ma-agents 4.x on BMAD v7. Its own text gets three load-bearing v7 contracts wrong: where setup writes answers, the shape and pending-only rule of `--module-answers`, and TOML's one-definition rule under marker blocks. It treats LLM-driven `bmad migrate` and `bmad status` as commands a Node CLI and CI can run. It relies on a `uv.toml` and an `npx` invocation that do not deliver the offline behaviour it promises. Epic 36 also still traces to the unimplemented v6.12 requirements (FR277–FR279, NFR74) and to v6 `module.yaml` requirements (FR104–FR106). Fix the three Critical and seven High findings, all of them text edits to F29, P5-11 and the Epic 36 traces, and the set will read as what the product owner asked for.
