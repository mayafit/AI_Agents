## Findings

- **The knowledge-store preflight breaks the no-dependency rule, and Epic 33 ships it broken.** A `git grep` for `## Knowledge Store Binding Preflight` finds the block in `bmad-knowledge` (going to `ma-knowledge`), `bmad-dev-epic` (going to `ma-ops-agents`) and the sprint skills (going to `ma-sprint`). The block does its stamp check with `node -e "const c=require('ma-agents/bin/cli.js')…"` (`lib/bmad-extension/skills/bmad-dev-epic/SKILL.md:115`). Epic 33 calls `ma-knowledge` and `ma-ops-agents` "zero-coupling seams", and 33.5 installs each one alone "with no ma-agents package present". Under that test the preflight `require` fails. The repoint to an in-skill script only happens later, in Epic 34 (34.5), and that script lives in `ma-atlassian-setup/scripts/` (`architecture/structure-and-boundaries.md`). So once repointed, `ma-knowledge`, `ma-ops-agents` and `ma-sprint` all depend at run time on `ma-atlassian`, which violates FR270 and P5-10.3. Fix: before Epic 33, decide where the stamp-check script lives (generated into every consuming skill like the shared text, or dropped when no store is bound), and give Epic 33 a story that repoints the preflight in the modules it carves.
- **Owned skills already reference skills that will land in other extensions.** `bmad-dev-epic` (going to `ma-ops-agents`) calls `git-workflow-skill` and `code-review` (`SKILL.md:195-204`, `checklist.md:18-36`, `references/story-pipeline.md:27-30`, `steps/step-03-epic-branch.md:21-23`). Both go to `ma-standards`. `skills/auto-bug-detection/SKILL.md:29` (going to `ma-standards`) sends users to `story-status-lookup` (going to `ma-sprint`). Story 32.5 AC1(b) even writes the test to accept names that resolve under root `skills/`, which bakes the cross-module resolution into a guard. No epic, story or pattern has a rule for this, or an audit for it. Proposal §5 assigns Gadi's SQA audit only to `bin/cli.js` references, shim names and duplicate leaves. Fix: add a per-module "every referenced skill is in this module, in upstream bmm/core, or behind a declared optional discovery with a fail-loud message" gate to Epic 33 (33.1 build or 33.5 release gate). Then decide whether `bmad-dev-epic` degrades without `ma-standards` or carries its own copy.
- **The package map does not assign every skill.** `lib/bmad-extension/skills/project-context-expansion/` and `skills/open-presentation/` (plus the training deck under `lib/methodology/`) appear in no package, in Proposal §4.1, in P5-10.1, or in the `structure-and-boundaries.md` target tree. The "Removed from `ma-agents` by Epic 35" list does not mention `lib/methodology/` either. Fix: assign each tracked skill directory to exactly one package, and add a test in 33.1 that fails if any source skill is unassigned.
- **Eleven skills exist in both source trees, and no story says which copy is canonical.** `add-sprint`, `add-to-sprint`, `cleanup-done`, `close-sprint`, `generate-backlog`, `modify-sprint`, `prioritize-backlog`, `remove-from-sprint`, `sprint-status-view`, `bmad-knowledge` and `my-next-issue` exist under both `skills/` and `lib/bmad-extension/skills/`. Epic 33 Wave 1 (33.3) says "move the root `skills/` tree" into `ma-standards`. Taken literally, that puts sprint, knowledge and Atlassian skills into `ma-standards`, with leaf names that collide with `ma-sprint`, `ma-knowledge` and `ma-atlassian`, which is exactly the duplicate-leaf abort NFR84 forbids. Fix: 33.3 should name the files it moves, and the plan should state which of the two copies each module takes, and how divergent copies are reconciled.
- **FR270 and FR272 contradict each other on the tracker-routing block.** FR270 (`prd/capabilities/bmad-integration-and-bundling.md:57`) and P5-10.2 make the "tracker-routing block" shared text that is generated into each consuming module. FR272 (`:59`) and the P2-11 amendment say the Jira branch lives once, in `ma-atlassian/references/jira-tracker.md`, and that sprint skills carry no Jira branch inline. Epic 34 Wave 1 (34.2) then says to strip the Jira block "into `shared/`-rendered hook-point stubs". If only `ma-atlassian` holds the routing text, nothing is shared. If sprint skills render it, FR272 is false. Fix: state what `shared/tracker-routing.md` actually contains (stub, or full block), and which modules consume it.
- **Generated shared text contradicts per-module versioning.** NFR85 (`bmad-integration-and-bundling.md:78`) says "a change in one module never forces a version bump in another", and `implementation-patterns.md` says "never bump a sibling". But editing `shared/knowledge-store-preflight.md` re-renders it into `ma-sprint`, `ma-knowledge` and `ma-ops-agents`, and the drift gate then forces all three to change content. No document says who owns `shared/` or `scripts/build.js`, or how a shared-text change is released across modules. The generator is a build-time coupling the no-dependency constraint does not account for. Fix: write down the ownership and release rule for `shared/`, and amend NFR85 to cover rendered-text changes.
- **The overlay's uninstall claim has no mechanism.** FR272 says "Removing `ma-atlassian` returns every sprint skill to file-system behaviour with no edit to the skill". The P2-11 amendment repeats it ("Removing the override (or the module)…"). But the overrides are files written into `_bmad/custom/<skill>.toml`, and bmad-method has no module-uninstall hook that would run `ma-atlassian-setup` in reverse. After removal, every bound skill still prepends a step that loads an adapter reference that no longer exists. No FR, decision or Epic 34 wave covers cleanup. Fix: give the setup skill an `unbind` operation, add an FR, and include an uninstall scenario in the 34.7 release gate.
- **Bind timing and install order are unspecified.** P5-10.4 has the setup skill walk the target table "for each target present on disk". Nothing says when it runs: whether bmad-method runs it during `install --yes` or the user invokes it, or what happens when `ma-sprint` (or a new upstream skill) is installed after `ma-atlassian`. In that case the new targets stay unbound and nothing reports it. Fix: specify the trigger (install, update, and any later module install), make re-binding idempotent, and test "atlassian first, sprint second" in 34.7.
- **Override collisions and the user layer, already solved in Story 31.15, are not carried forward.** The marker-delimited TOML design in P5-10.4 does not mention a user-authored `_bmad/custom/<skill>.toml` that already sets the same key (`activation_steps_prepend`, `workflow.tracker`), duplicate-key parse failures (which become exit 1 at 6.11+, per 32.7's own premise), or the `<skill>.user.toml` scalar-over-array discard that `detectUserLayerScalarOverrides` (`lib/confluence-publish-hook.js:1708`) exists to catch. Story 31.15 took five fix rounds to close exactly this (sprint-status `31-15` entry). Fix: make the 31.15 collision predicate and user-layer detection a stated requirement of FR273, not something left implicit in code that 34.5 "relocates".
- **Upstream renames and version drift after bind are unhandled.** The target table is keyed to the installed bmad-method version, but extensions install on vanilla bmad-method (FR269), and those users can update bmad-method independently of any ma-agents qualification. Nothing defines (a) behaviour on a version missing from `targets.yaml` (fail, nearest, or refuse), (b) a re-bind on `bmad-method install --action update`, or (c) the removal of orphaned overrides when a target skill is renamed. FR271's "latest the team has qualified" cannot bind vanilla users. Fix: add an FR for unlisted-version behaviour and a re-bind-on-update rule. The readiness look-ahead (Epic 34 item (c)) raised this, and it is still unassigned.
- **Story 32.4 deletes irreversibly before anyone proves the restoration path exists.** 32.4 deletes our `bmad-sprint-planning` and records the Jira, preflight and 31.9-gate loss as "interim until Epic 34". But the existence of a usable hook on upstream `bmad-sprint-planning`, `bmad-build` and `bmad-build-auto` is only checked in 34.1, which explicitly says "STOP if an upstream target has no usable hook". 32.1 AC9(d) records `customize.toml` keys for `bmad-build` only, and never checks `bmad-sprint-planning` or `bmad-build-auto` for an `activation_steps_prepend` (or equivalent) slot. If 34.1 stops, the "interim" limitation becomes permanent, with Epic 32 already shipped. Fix: extend 32.1 AC9(d) to every FR273 target, and make "a hook slot exists" part of 32.4's GO line.
- **The C-4 closure guard can clear the known limitation for the wrong reason.** 32.4 AC8's test removes the CHANGELOG limitation once a vendored `lib/extensions/ma-atlassian/**/targets.yaml` "lists `bmad-sprint-planning` as a target". But FR273 already listed `bmad-sprint-planning` as a Jira target before the C-4 amendment. A table that binds only the Jira role satisfies the guard while the preflight and 31.9 gate (the `confluence-read` role) remain missing. Fix: the guard must check for the `confluence-read` role on all three skills (`bmad-sprint-planning`, `bmad-build`, `bmad-build-auto`), not just that the name appears.
- **The C-4 "discharge" left the architecture behind.** FR273 was amended to add `bmad-sprint-planning`, `bmad-build` and `bmad-build-auto` as Confluence-read targets. But the P2-11 amendment (`architecture/decisions/sprint-and-backlog-management.md`, "Upstream skills are bound the same way") lists them only as tracker targets. P5-10.4 has no target list, and Epic 34's wave text never mentions the three new Confluence-read bindings. The readiness report itself defers this ("*PM to confirm when storying Epic 34*"), so the condition was re-labelled, not discharged. Fix: update P2-11/P5-10.4 and the Epic 34 34.4/34.6 scope text now.
- **The proposal says nothing is in flight, and that is false.** Proposal §2 "Story impact" says "No in-flight stories. All open work in `sprint-status.yaml` is done or cancelled; the backlog is empty", and calls Epic 31 "done (v3.18.0)". `sprint-status.yaml` shows `epic-31: in-progress` with `31-14-…` and `31-16-…` in `review`, `ds-1-…` in `in-progress`, Epic 19 stories `ready-for-dev`, Epic 23 (`23-2-convert-gad-to-memory-agent`: Gadi moves to `ma-ops-agents`), and at least ten `bug-*` entries in `backlog` or `review`. Some are directly affected by the split: `bug-custom-marketplace-stage-survives-install…` becomes moot under the FR239–FR243 retirement, `31-16` manifest-aware sweep governs the very upgrade path 32.4 AC4 relies on, and `bug-npm-test-windows-suite-health-chain` is cited by 32.9. Fix: add a disposition table for every open item (carry, re-home, cancel), and correct the Epic 31 status claim.
- **There is no migration story for existing 3.x installs.** Epic 35 removes `lib/bmad-extension*` and the `ma-skills` module, yet no FR or story covers: projects whose `_bmad/_config/manifest.yaml` records module `ma-skills` from a staged custom source that will no longer exist on update; `.ma-agents.json` entries for root-`skills/` content that `bmad-method` will now install under five new module codes with the same leaf names; Epic 31 `_bmad/custom/<skill>.toml` publish hooks that invoke `ma-agents confluence-plan`, a command 35.2 deletes; and whether `ma-atlassian-setup` recognises and replaces the old markers. Fix: add a 35.x migration story with a fixture of a real 3.18.1 project (including Epic 31 overrides), and FRs for module-code migration and old-override replacement.
- **Cline wrappers and IDE injection have no owner on the vanilla path.** FR209/FR210 (Cline wrapper reconciliation) live in ma-agents' `deployClineWorkflows` (`lib/bmad.js:1876`). FR274 keeps only "IDE instruction-block injection" in the thin installer, and FR269 promises full operation without the ma-agents package. So a vanilla `--custom-source` install gets no `.clinerules/workflows/` wrappers for any extension skill. Separately, `ma-standards-setup` (33.3) also injects into `AGENTS.md`, `.roomodes`, `.clinerules`. That makes three writers to the same files (installer injection, `ma-standards-setup`, upstream `bmad-project-context`), and FR274's "performs no project-scoped work an extension's setup skill performs" is contradicted by keeping injection in the installer. 32.8 tests only two writers. Fix: assign Cline wrappers and rule injection to exactly one owner, and extend the two-writer test to the real writer set.
- **Nothing proves the offline claim for vanilla installs.** Proposal §3 claims "every extension works on a plain `npx bmad-method install --custom-source <src> --modules bmm`, online or offline, with or without the ma-agents installer". NFR84 and 33.5 only require "a clean machine", with no `--network none`. A vanilla air-gapped install also needs `npx` and bmad-method itself from a local source, a local-path `--custom-source` (not a git URL), and pre-seeded `uv`/Python. No story covers any of that. The only offline proof is 35.4, which goes through the ma-agents tarball. Fix: either withdraw "offline … without the ma-agents installer" from the proposal and FR269, or add a 33.5/34.7 air-gapped vanilla scenario.
- **Single-module selection from a five-plugin marketplace under `--yes` is unverified.** The 33.5 gate runs `npx bmad-method install --custom-source <repo> --modules bmm … --yes` and expects one module "alone". The marketplace lists five plugins in discovery mode, and nothing shows how a non-interactive install selects one, rather than installing all five or none. FR240 needed a dedicated spike (Story 30.5) for exactly this subset question at 6.10. Fix: add that question to an Epic 33 Wave-0 spike, or to 32.1, before 33.5's command is written into a gate.
- **The air-gap spike tests the wrong scripts.** 32.1's own context says `bmad-build`/`bmad-build-auto` "render through `render_skill.py` and HALT on activation if `uv` is unavailable". Yet 32.1 AC4 (the gate question) and 32.9 AC1(d) exercise only `resolve_customization.py` and `resolve_config.py`. If `render_skill.py`, or the skill's own scripts such as `sprint_plan.py`, declare PEP 723 dependencies or need a different interpreter path, PASS can be recorded while `bmad-build` still halts offline. Fix: add `render_skill.py` (driven as `bmad-build` activation does) and `sprint_plan.py` to the seeded and unseeded `--network none` runs in 32.1 AC4 and 32.9 AC1.
- **The `uv` "prerequisite" is never detected.** FR277 makes `uv` + Python 3.11 "stated prerequisites of every ma-agents install", while NFR74 clause 1 and 32.2 AC6 require the install to succeed without them. The only check is a Dev Note in 32.5 ("the intake step should check `uv --version` once"), which is not an AC. The result is exactly the failure mode 32.1 calls the central risk: a green install, then a halt at first activation. Fix: add an AC (installer post-install notice, and the `bmad-dev-epic` intake check) so the missing prerequisite is reported at install time without changing the exit code.
- **32.5 ignores concurrent `sprint-status.yaml` writers.** 32.1 AC9(g) asks whether `bmad-build`/`bmad-build-auto` write to `sprint-status.yaml`, and the readiness report (F-8) calls that a schema risk. Fix: add an AC to 32.5 that depends on the 32.1 AC9(g) answer (serialize status writes in the orchestrator, or suppress them in subagents).
- **The `bmb` "latest stable tag" makes cache builds non-reproducible.** 32.3 AC3 has the builder clone "the latest stable release tag" of `bmb` when the registry leaves it unpinned. Two `npm run build:bmad-cache -- --force` runs of the same commit on different days can then produce different caches. That conflicts with NFR21 (deterministic output for the same package version) and the story's own "no upstream release cut after this ma-agents version can reach my install".
